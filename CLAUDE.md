# Vesper — agent notes

- AGENTS.md is a symlink of CLAUDE.md, so you only ever need to update CLAUDE.md when finishing work and additional notes are needed.
- This app is documented system-by-system in `docs/` — **read `docs/README.md` first**, then the doc for whichever system you touch. Update the relevant doc in the same change when behavior or patterns shift.
- If a _reference_ docs (the root docs and docs/guide/ folders) would exceed ~400 lines after creation or editing, determine if you can split it into more specific docs. A good example is `contracts.md` which was at one point thousands of lines, so we are creating a contracts folder and putting more specific documents in that folder rather than keeping one large file.
- Because this app is in ongoing development you _do not_ need to preserve legacy functionality when changing features and systems. Prefer removing old code rather than marking deprecated or making wrappers to preserve functionality.
- Resilience rules in `docs/resilience.md` are mandatory: `parseOr` at every trust boundary, diagnostics over exceptions, degraded defaults over failed turns.
- `src/contracts` and `src/lib` are pure (no IO/env/db). Server modules import each other only through `index.ts` barrels. Components never import `server/*`. These boundaries are enforced by an ESLint `no-restricted-imports` rule (`eslint.config.mjs`) — a violation fails `pnpm lint`.
- Registries (attributes, meters, fact kinds, body locations) are the extension points — vocabulary changes are data edits in one file, never schema migrations.
- DB workflow: edit `src/server/db/schema.ts` → `pnpm db:generate` → review SQL in `drizzle/` → `pnpm db:migrate`. Never `drizzle-kit push`. The initial migration (`drizzle/0000_*.sql`) begins with `CREATE EXTENSION IF NOT EXISTS vector`, so `pnpm db:migrate` self-enables pgvector and works on a fresh database without `pnpm db:create` (drizzle-kit does not emit this line — preserve it when regenerating the baseline migration).
  - **Never fake a TTY to auto-answer `db:generate`'s interactive create-vs-rename prompt.** Wrappers like `yes "" | script -qec "pnpm db:generate" /dev/null` (any unbounded input generator — `yes`, `while true; echo` — piped into a PTY emulator like `script`/`expect`/`unbuffer`) run away to multi-GB RAM and trip the machine's OOM killer (see memory `machine-earlyoom-oom-tuning`). When drizzle can't tell a rename from a create+drop it blocks on an arrow-key prompt; that prompt means the schema diff is ambiguous and needs a **human decision** — stop and ask the user to run `pnpm db:generate` themselves (suggest the `!` prefix), don't try to push through it.
- Tests: `pnpm test` (pure), `pnpm test:int` (needs Postgres). Degradation tests assert fallback **and** diagnostic code.

- Before claiming a task done, run `pnpm verify` (lint + typecheck + test + jscpd) — it must pass. Lint is **type-aware** and runs at `--max-warnings 0`; a pre-commit hook (husky + lint-staged) re-lints staged files. Enforced agent-guardrails (`eslint.config.mjs`): no `any`/unsafe, no floating promises, exhaustive `switch`, no import cycles, and the module-boundary + provider-gateway (`@openrouter` only in `src/server/ai`) import rules. jscpd is a copy-paste regression gate (don't recreate utilities — reuse via the barrels).
- Git: after each **major task** (a feature or chore), write a descriptive, conventional-style commit message (`feat:` / `chore:` / `docs:` …) and push to `origin`. Minor bug fixes and small improvements don't need their own commit-and-push — fold them into the next major task's commit.
- Working docs (`docs/developer-notes/`) use a **topic-named** convention — filenames encode _what_, never _when_. Priority order lives only in `roadmap.md`, so resequencing work never renames a file (the old `phase-N` scheme baked order into filenames and forced churny renames; don't reintroduce it).
  - **Plans** are `<topic>.plan.md` (e.g. `scene-images.plan.md`); the matching design/decision detail is `<topic>.spec.md`, post-ship fixes are `<topic>.followups.md`, and finer detail is `<topic>.<subtopic>.md`. Same topic slug ⇒ they nest together in the editor and `grep <topic>` finds every pointer (a stable target that doesn't rot on resequencing).
  - Every plan opens with a `Status:` line — **draft** (not settled / placeholder), **next** (queued), **active** (in progress), **shipped — <date>** (with a completion note naming leftovers and where they went), or **parked**.
  - `roadmap.md` is the single ordered index of plans by current priority (+ a "someday" bucket pointing at `deferred.plan.md`, and a **Shipped** history at the end). It is the source of truth for what to build next and what's been done — **consult it whenever starting major-feature work**, and **keep it current as part of that work** (an out-of-date roadmap is a bug).
    - **Work the roadmap order.** Default to building the top of `## Next`. Sometimes something must be built out of order (an urgent fix, a fast one-off) — that's allowed, but it **still gets a roadmap line** (added to `## Next`/`## Active` before or as you start, never built invisibly). Nothing of consequence gets built without appearing here.
    - **On completion, always update the roadmap** in the same change: move the finished entry into `## Shipped` (newest-first, terse — one line: bold title — plan link · spec — `— <date>` — a short hook; full detail stays in the plan, not the roadmap), set the plan's `Status:` to `shipped — <date>`, and drop it from `## Active`/`## Next`. Partially-shipped work (e.g. one slice of many) gets a Shipped line for the slice **and** stays in Next for the remainder, each cross-referencing the other.
    - **Reordering is allowed but should be rare** — a one-line move (never a file rename), and only a deliberate reprioritization, not incidental churn. Don't silently reshuffle while doing unrelated work.
  - Open questions raised anywhere in a topic's docs are restated in that topic's **plan** under an `## Open questions` section, each linking to the detail; resolving one = remove it from the plan and record the ruling in the detail doc.
  - Unplanned-but-good ideas not yet promoted to a plan are parked in `deferred.plan.md` (the parking-lot anchor); supporting detail is `<topic>.deferred.md`. When an idea graduates it becomes a `<topic>.plan.md`, gets a `roadmap.md` line, and leaves `deferred.plan.md` (a one-line "graduated → …" tombstone is fine).
  - **Legacy `phase-N` docs** (`phase-N-plan.md`, `*.phaseN.md`, `followups.phaseN.md`) are the historical record of already-run phases — left as-is, not renamed. New work never uses phase numbers.
- This folder is its own pnpm root (see `pnpm-workspace.yaml`); run pnpm commands from here, not the repo root.
