# Vesper — agent notes

- AGENTS.md is a symlink of CLAUDE.md, so you only ever need to update CLAUDE.md when finishing work and additional notes are needed.
- This app is documented system-by-system in `docs/` — **read `docs/README.md` first**, then the doc for whichever system you touch. Update the relevant doc in the same change when behavior or patterns shift.
- **Writing or editing any Markdown under `docs/`? Invoke the `vesper-docs` skill first** (`.claude/skills/vesper-docs/`). It carries the procedure for both tiers — reference docs in `docs/`, working docs in `docs/developer-notes/` — plus the four rules that live nowhere else: one canonical owner per fact, the `Outcome:` line every plan opens with, the conversation-residue guardrail, and the pre-finish validation checklist. Document templates (plan, spec, trial, audit, deferred stub, reference doc) are in `.claude/skills/vesper-docs/templates/` — copy the file rather than improvising the section order.
  - The tier split is the whole discipline: **reference docs say what is true now** (present tense, dateless, no plans, no history); **working docs say what we are doing about it** (dated, directional, status-carrying). When one file tries to do both jobs, split it.
- If a _reference_ doc would exceed ~400 lines after creation or editing, determine if you can split it into more specific docs. A good example is the old `contracts.md`, once thousands of lines, now split into the `docs/contracts/` folder of focused per-topic docs. **This guideline covers the reference tier only** — the root `docs/` files and its topic folders (`docs/guide/`, `docs/contracts/`, `docs/character-chat/`, `docs/image-models/`, …). **It does not apply to `docs/developer-notes/` or its subfolders**: a plan, spec, trial, or audit is as long as its subject requires, and a long working doc is not a defect. Split those on content — separate domains a reader needs individually, parts edited independently by different work, or spec-grade detail sitting in a plan — never to hit a line count.
- Because this app is in ongoing development you _do not_ need to preserve legacy functionality when changing features and systems. Prefer removing old code rather than marking deprecated or making wrappers to preserve functionality.
- **Product direction (owner, 2026-07-13; realized 2026-07-22): character chat was the test bed for the successor world model — that successor is now live, and the legacy world/session model is deleted.** Rollout R6 (`docs/developer-notes/finished/engine.rollout.plan.md`) removed the old world/session-model code and tables outright. Two lanes remain and stay **separate**: legacy character chat, and successor chats (a chat bound to its own simulated world, born through the `/worlds` front door, engine-authoritative per the per-chat `engine_authority` flag). New interaction/state/narration patterns still get proven in the chat lane first; when a feature could land in either lane, chat leads.
- Resilience rules in `docs/resilience.md` are mandatory: `parseOr` at every trust boundary, diagnostics over exceptions, degraded defaults over failed turns.
- `apps/web/src/contracts` and `apps/web/src/lib` are pure (no IO/env/db). Server modules import each other only through `index.ts` barrels. Components never import `server/*`. These boundaries are enforced by an ESLint `no-restricted-imports` rule (`eslint.config.mjs`) — a violation fails `pnpm lint`.
- **This is a pnpm workspace: the Next app is `@vesper/web` under `apps/web`, plus packages under `packages/`, plus the repository root itself — which stays a workspace because it owns the operational surface (`scripts/`, `drizzle/`, deployment files, every repo-wide gate).** A package may not import the app — neither `@/…` nor a relative path climbing out of the package (both spellings reach the same modules; both are lint-enforced) — so the dependency runs one way only, and another package is imported by name, never by path. When a package looks like it needs something from the app, pass the value in as an argument or leave the code in the app; do not invert it. Today there are three packages: `@vesper/image-core` (the provider-neutral image engine: capabilities, models/profiles, LoRAs, render intent, render kernel, references, identity packs, lab contracts, crop geometry, provider interface), `@vesper/contracts` (the shared foundation — the diagnostic contract and `parseOr`, and nothing else; `apps/web/src/contracts/diagnostics.ts` and `apps/web/src/lib/parse.ts` are re-export barrels over it, so app import paths are unchanged), and `@vesper/image-replicate` (the **server-only** Replicate transport: predictions, uploads, output download, schema probing — it reads no environment, and `apps/web/src/server/ai/replicate-runtime.ts` is the only code that reads `REPLICATE_*` and hands it one configured client per process). `apps/web/src/server/images` keeps everything stateful and Vesper-specific. The migration that produced this layout — packages, then the app move — is `docs/developer-notes/finished/monorepo-image-core.plan.md`, with one spec per slice indexed from its sibling spec hub; the package's own contract is in `packages/image-core/README.md`. Packages ship TypeScript source with no build step and are resolved by name through the workspace link and their `exports` map — **no tsconfig path alias, no Vitest alias** (both were removed so a broken manifest can't hide behind them). Adding a package means: its `package.json` with a `"."` export, its own dependencies, and its own `typecheck` + `test` scripts; a package `tsconfig.json` and — if it has tests — a package `vitest.config.ts` (environment node, `src/**/*.test.ts`, no alias, no setup file) listed in that tsconfig's `include` so type-aware lint can parse it; a rank + runtime target in the layer policy in `scripts/check-workspace-imports.ts`; `transpilePackages` in `apps/web/next.config.ts`; and the Dockerfile's manifest COPY. **There is no root script to edit and no root Vitest project to add** — see the validation-ownership note below. The last two ARE explicit, because Docker and Next cannot read pnpm's workspace graph and both fail late and namelessly; `scripts/workspace-registration.test.ts` is the tripwire that fails when either drifts. The layer rank and the `exports` map need no tripwire — the two boundary gates below already report an unranked package (`package-layer-unknown`) and an unresolvable one. **The boundary is checked by `pnpm lint:package-boundaries`, not by lint spelling rules** — it resolves every import, so a relative escape, an undeclared code subpath (`@vesper/x/src/...`), an undeclared dependency, a wrong-direction package edge, a published-entry `export *`, or a Node-only import inside a browser-portable package all fail. A package may publish **exact** subpath entries in its `exports` map (never a `*` pattern), and each declared entry is public API on the same terms as the root; `pnpm lint:package-resolution` separately imports every declared entry of every package by its public specifier. Both run in the `static` gate of `pnpm verify`.
  - **The app is started only through the root launcher, `scripts/web.mjs`** (`pnpm dev` / `build` / `start`, and the Docker `CMD`). It runs Next with `apps/web` as the project directory while establishing two repository-level facts first: `DATA_ROOT` defaults to the repository's `data/` (not the Next project's), and the repository-root `.env` is loaded (Next would not see it from `apps/web`). There is deliberately one loader — do not add a second `.env`, and do not add env loading to `next.config.ts`, which `next start` never executes. On Fly, `DATA_ROOT=/app/data` is set explicitly in the Dockerfile so the invariant never depends on the working directory.
  - **Root scripts may import application source through `@/…`** (root `tsconfig.json` maps it to `apps/web/src`, and `tsx` honours it). That is the one sanctioned cross-workspace edge; a relative path into `apps/web` is not, and `pnpm lint:package-boundaries` fails it.
  - **Each workspace owns its own `typecheck`/`test` scripts; the root orchestrates by recursion, never by enumerating workspace names.** Root `pnpm typecheck` checks the root project and then runs `pnpm -r --workspace-concurrency=1 run typecheck`; root `pnpm test` runs the root Vitest config's `app` project and then `pnpm -r --workspace-concurrency=1 run test`. `pnpm -r` excludes the root workspace, so neither self-recurses, and **serial workspace concurrency is mandatory** on this 16 GB machine — never widen it. A package joins both gates by owning the scripts and a `vitest.config.ts`; a workspace without a `test` script is simply skipped, which is why **`apps/web` defines `typecheck` but deliberately no `test`**: its suite is the root config's `app`/`app-int` projects, which need the repository root as cwd (tests resolve repo-relative paths through `process.cwd()`), the `@/` alias, and the demo-mode setup file — and which also claim the `scripts/**` tripwire tests, so no config inside `apps/web` could own them. Detail: `docs/testing.md` and the header comment in `vitest.config.ts`.
- **JSX prose-boundary whitespace:** standard JSX drops the space when a line break separates `{expr}`/`</el>` from the prose that follows — guard wrapped boundaries with `{" "}` or a string-expression child. On top of that, next 16.2.x's vendored swc drops the **leading** space of a multi-line JSX text node that contains an HTML entity (upstream regression swc-project/swc#11474, fixed by swc#11521; next ≥16.3.0 carries the fix) — entity-bearing wrapped prose after an expression shipped glued ("…everything Sabrinaremembers…") until converted to explicit string-expression children (`{" remembers …"}`). Keep that idiom for prose straddling an expression/element boundary, and prefer literal `’ “ ”` characters over entities inside prose.
- Registries (attributes, meters, fact kinds, body locations) are the extension points — vocabulary changes are data edits in one file, never schema migrations.
- DB workflow: edit `apps/web/src/server/db/schema.ts` → `pnpm db:generate` → review SQL in `drizzle/` → `pnpm db:migrate`. Never `drizzle-kit push`. The initial migration (`drizzle/0000_*.sql`) begins with `CREATE EXTENSION IF NOT EXISTS vector`, so `pnpm db:migrate` self-enables pgvector and works on a fresh database without `pnpm db:create` (drizzle-kit does not emit this line — preserve it when regenerating the baseline migration).
  - **Never fake a TTY to auto-answer `db:generate`'s interactive create-vs-rename prompt.** Wrappers like `yes "" | script -qec "pnpm db:generate" /dev/null` (any unbounded input generator — `yes`, `while true; echo` — piped into a PTY emulator like `script`/`expect`/`unbuffer`) run away to multi-GB RAM and trip the machine's OOM killer (see memory `machine-earlyoom-oom-tuning`). When drizzle can't tell a rename from a create+drop it blocks on an arrow-key prompt; that prompt means the schema diff is ambiguous and needs a **human decision** — stop and ask the user to run `pnpm db:generate` themselves (suggest the `!` prefix), don't try to push through it.

The wider `test:int` suite is not part of any gate — run it by hand when the surface it covers moves. Degradation tests assert fallback **and** diagnostic code.

- Validation is **LOCAL and PUSH-GATED — there is no GitHub Actions CI.** The workflow was deleted when Actions minutes ran out. `scripts/verify.sh` (`pnpm verify`) is the only gate now, and `.husky/pre-push` runs it automatically, so nothing reaches GitHub unverified. **The old "never run gates locally" rule is reversed** — local gates are the workflow, and every CI-era procedure (`gh pr ready`, `gh pr checks --watch`, `gh workflow run CI`, the draft-PR dance, the `verify` status check) is dead vocabulary.
  - **`pnpm verify` runs the gates SERIALLY** — one at a time, each inside a memory-capped systemd scope, refusing to start below ~4.5 GiB available RAM. That serialization is the whole point on this 16 GB machine: never run the gates as a parallel chain, spread across concurrent shells, or alongside a Docker build or dev server. Target `all` (the default) is lint → static checks (`lint:cycles`, `lint:authz`, `lint:package-boundaries`, `lint:package-resolution`) → typecheck → pure tests → jscpd. It runs the whole set rather than stopping at the first failure, then prints per-gate durations and names every gate that failed.
  - **The pre-push hook is the guarantee, so you don't have to remember.** `.husky/pre-push` invokes `scripts/verify.sh all` on any push that touches code; documentation-only pushes (every changed path under `docs/` or ending `.md`) and branch deletions skip it. Run `pnpm verify` by hand only when you want the feedback earlier than push time. `VESPER_SKIP_GATES=1 git push` and `git push --no-verify` opt out — for when you have just run the gates yourself and don't want to pay twice, **never to push past a failure**. In a fresh worktree with no `node_modules` the hook fails loudly instead of pretending to verify: `pnpm install` there, or push with `--no-verify` from a checkout that has dependencies.
  - Individual targets exist for tight loops: `bash scripts/verify.sh lint|static|typecheck|test|jscpd`. Two more sit outside `all` because they need infrastructure or minutes of wall-clock — **`engine`** (needs `pnpm db:up && pnpm db:migrate`; runs `test:engine` in strict mode plus the Gate 1 benchmark, and hard-fails rather than self-skipping when the database is down) and **`build`** (the Next production build, heap-pinned to the Fly builder's 4 GB ceiling).
  - **Before every `fly deploy`, run `pnpm verify:full` on main** — `all` + `engine` + `build`, with the dev database up. Nothing else compiles the app before Fly does, so skipping it means `fly deploy` is the first thing to build the change. Runbook: `docs/deployment.md`.
  - **For documentation-only changes** (only Markdown files and/or files under `docs/`), the gates skip themselves — review the rendered Markdown, links, and internal consistency instead.
  - To write compliant code the first time, know what the gates enforce: type-aware lint at `--max-warnings 0` with agent guardrails (`eslint.config.mjs` — no `any`/unsafe, no floating promises, exhaustive `switch`, module boundaries, provider gateway `@openrouter` only in `apps/web/src/server/ai`), circular-import detection via madge, workspace-boundary and package-resolution checks (`lint:package-boundaries`, `lint:package-resolution`), and jscpd as the copy-paste regression gate (it lists the offending clones). The pre-commit hook (husky + lint-staged) lints staged files at commit time, so lint failures usually surface well before the push gate.
  - **`.github/workflows/promote.yml` is the only workflow left** — a manual button that opens the `main` → `prod` PR. Don't add another; a new workflow is a new bill.
- Git: after each **major task** (a feature or chore), write a descriptive, conventional-style commit message (`feat:` / `chore:` / `docs:` …). **Code, configuration, dependency, or workflow changes reach `main` via a branch + PR** — the pre-push gate is the only validation they ever get, so never bypass it and never push code commits directly to `main`. Draft vs. ready no longer signifies anything (nothing runs on GitHub); open a draft while iterating if you like, and merge once the gate passed and the review is done. Documentation-only changes are the exception: commit and push them straight to `main`. Minor bug fixes and small improvements don't need their own PR — fold them into the next major task's branch.
  - **`git doc`** is the owner's shortcut for that documentation-only path — a global alias for `git add -A && git commit -m "documentation updates" && git push`. Use it to land Markdown/`docs/` work on `main` (the pre-push hook detects a documentation-only push and skips the gates). Because it stages **everything**, first confirm the worktree holds nothing but doc changes (`git status --short`) — concurrent sessions stage WIP in this checkout, so if any code is present, commit by pathspec with a real `docs:` message instead. `git wip` (`add -A` + `wip` + push) remains the owner's scratch equivalent.
- Working docs (`docs/developer-notes/`) use a **topic-named** convention — filenames encode _what_, never _when_. Priority order lives only in `roadmap.md`, so resequencing work never renames a file (the old `phase-N` scheme baked order into filenames and forced churny renames; don't reintroduce it).
  - **Plans** are `<topic>.plan.md` (e.g. `scene-images.plan.md`); the matching design/decision detail is `<topic>.spec.md`, post-ship fixes are `<topic>.followups.md`, and finer detail is `<topic>.<subtopic>.md`. Same topic slug ⇒ they nest together in the editor and `grep <topic>` finds every pointer (a stable target that doesn't rot on resequencing).
  - **A plan/spec pair whose parts are edited independently splits into a hub + unit docs** — the trigger is that separate work keeps touching separate sections, not the file's length. The engine docs are the model: one `engine.gateN.<slug>.md` per gate (future gates included; gate numbers are stable architectural identities, not the banned reorderable `phase-N`), `engine.spec.<cluster>.md` files carrying globally-numbered § ranges, and `engine.plan.md` / `engine.spec.md` remaining as thin index hubs so every existing link and "§N" citation still resolves. Convention detail: `docs/developer-notes/CLAUDE.md` §"Engine gate docs".
  - Every plan opens with a `Status:` line — **draft** (not settled / placeholder), **next** (queued), **active** (in progress), **awaiting acceptance** (every slice built; waiting on the trial, owner review, or flag enable the plan names), **shipped — <date>** (the WHOLE plan delivered and accepted, with a completion note naming leftovers and where they went), or **parked** — and then an **`Outcome:` line**: one sentence, `<A player | The owner | A developer> can <do something concrete> so that <observable consequence>.` It names a person (never a system), promises something observable (never "more robust/reliable/polished"), and uses no vocabulary a first-time reader wouldn't know. If you can't write it, the work isn't understood well enough to plan. The roadmap keeps its own prose hook per entry, but that hook must not contradict the plan's Outcome line. Non-plan docs carry a Status line saying what they are (`companion to …`, `detail for …`, `reference (audit run <date>)`, `closed — <verdict> <date>`) and no Outcome line. Full rules and templates: the `vesper-docs` skill.
  - `roadmap.md` is the single ordered index of plans by current priority (+ a "someday" bucket pointing at `deferred.plan.md`, and a **Shipped** history split out into the sibling `roadmap.shipped.md`). It is the source of truth for what to build next and what's been done — **consult it whenever starting major-feature work**, and **keep it current as part of that work** (an out-of-date roadmap is a bug).
    - **The `## To be Planned` section (above the priority lists) is the owner's intake — never add to it.** It holds raw feature/improvement ideas the product owner wrote for themselves; agents **must not** add, edit, or reword entries there. Only act on it **on request**: when asked to plan one of its items, create the new `<topic>.plan.md` (or fold the idea into an existing plan), add the corresponding line to `## Next`/`## Active` below, and **then remove the now-planned item from `## To be Planned`** in the same change. Don't promote items unprompted.
    - **Work the roadmap order.** Default to building the top of `## Next`. Sometimes something must be built out of order (an urgent fix, a fast one-off) — that's allowed, but it **still gets a roadmap line** (added to `## Next`/`## Active` before or as you start, never built invisibly). Nothing of consequence gets built without appearing here.
    - **Record every finished piece of work one rung up — the progress ladder.** A finished **slice** is recorded in its **spec** (which owns implementation status for its area); a finished **spec** is recorded in its **plan**; a finished **plan** is recorded in **`roadmap.shipped.md`**. Dev work that has landed and is not written into its governing doc is unfinished work — updating that doc is part of the same change, never a follow-up. Work that is built but not yet accepted (a trial unrun, an owner review pending, a flag still dark) is recorded as exactly that, in the same place; "built" is never written as "shipped".
    - **`roadmap.shipped.md` holds COMPLETED PLANS only, one line each.** A slice, a spec, or a bug fix never earns an entry — those live in the spec and plan that govern them. The line is: bold title — link to the plan in `finished/` — `— <date>` — a short hook, and nothing more. When a plan completes, in one change: set its `Status:` to `shipped — <date>`, `git mv` it and its specs to `finished/`, drop it from `## Active`/`## Next` in `roadmap.md`, and add the one line. **Keep long detail out of both files** — `roadmap.md` and `roadmap.shipped.md` are indexes, and an entry that grows past a sentence or two is a plan leaking into its index.
    - **Reordering is allowed but should be rare** — a one-line move (never a file rename), and only a deliberate reprioritization, not incidental churn. Don't silently reshuffle while doing unrelated work.
  - Open questions raised anywhere in a topic's docs are restated in that topic's **plan** under an `## Open questions` section, each linking to the detail; resolving one = remove it from the plan and record the ruling in the detail doc.
  - Unplanned-but-good ideas not yet promoted to a plan are parked in `deferred.plan.md` (the parking-lot anchor); supporting detail is `<topic>.deferred.md`. When an idea graduates it becomes a `<topic>.plan.md`, gets a `roadmap.md` line, and leaves `deferred.plan.md` (a one-line "graduated → …" tombstone is fine).
  - **Archiving shipped docs → `finished/` (part of ship close-out; only the two roadmap files repoint).** Once a plan's `Status:` is `shipped` — which happens only when the WHOLE plan is delivered and accepted — `git mv` its `<topic>.plan.md` / `.spec.md` (and any `<topic>.*` detail docs) into `docs/developer-notes/finished/` in the same change — an un-archived shipped plan is folder rot (rule detail: `docs/developer-notes/CLAUDE.md` §"Ship close-out"). A plan with slices still queued does NOT move: it stays put, keeps its roadmap line, and records its progress in its spec. When you do move one, **`roadmap.shipped.md`'s new line MUST use the `finished/…` path** — it is the always-current index and must never carry a broken link. Every OTHER inbound link (sibling plans/specs, detail docs) is **left pointing at the old path — do not repoint them, and don't fix the moved doc's own outbound links either.** Repointing those is churn with little payoff: shipped docs are rarely reopened, so their stale links don't matter, and `grep <topic>` still finds both the moved file and its referrers. (This is the deliberate exception to the docs/README.md "repoint active inbound links" rule, which still applies to **live** system docs.) Moving plan+spec together keeps their mutual relative links resolving.
  - **Legacy `phase-N` docs** (`phase-N-plan.md`, `*.phaseN.md`, `followups.phaseN.md`) are the historical record of already-run phases — left as-is, not renamed. New work never uses phase numbers.
- This folder (the repo root) is its own pnpm installation root — `pnpm-workspace.yaml` pins it so pnpm never resolves a parent directory's workspace metadata. Run all pnpm commands from here, never from a parent directory.
