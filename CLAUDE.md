# Vesper — agent notes

- AGENTS.md is a symlink of CLAUDE.md, so you only ever need to update CLAUDE.md when finishing work and additional notes are needed.
- This app is documented system-by-system in `docs/` — **read `docs/README.md` first**, then the doc for whichever system you touch. Update the relevant doc in the same change when behavior or patterns shift.
- **Writing or editing any Markdown under `docs/`? Invoke the `vesper-docs` skill first** (`.claude/skills/vesper-docs/`). It carries the procedure for both tiers — reference docs in `docs/`, working docs in `docs/developer-notes/` — plus the four rules that live nowhere else: one canonical owner per fact, the `Outcome:` line every plan opens with, the conversation-residue guardrail, and the pre-finish validation checklist. Document templates (plan, spec, trial, audit, deferred stub, reference doc) are in `.claude/skills/vesper-docs/templates/` — copy the file rather than improvising the section order.
  - The tier split is the whole discipline: **reference docs say what is true now** (present tense, dateless, no plans, no history); **working docs say what we are doing about it** (dated, directional, status-carrying). When one file tries to do both jobs, split it.
- If a _reference_ doc (the root `docs/` files and the `docs/guide/` folder) would exceed ~400 lines after creation or editing, determine if you can split it into more specific docs. A good example is the old `contracts.md`, once thousands of lines, now split into the `docs/contracts/` folder of focused per-topic docs.
- Because this app is in ongoing development you _do not_ need to preserve legacy functionality when changing features and systems. Prefer removing old code rather than marking deprecated or making wrappers to preserve functionality.
- **Product direction (owner, 2026-07-13; realized 2026-07-22): character chat was the test bed for the successor world model — that successor is now live, and the legacy world/session model is deleted.** Rollout R6 (`docs/developer-notes/finished/engine.rollout.plan.md`) removed the old world/session-model code and tables outright. Two lanes remain and stay **separate**: legacy character chat, and successor chats (a chat bound to its own simulated world, born through the `/worlds` front door, engine-authoritative per the per-chat `engine_authority` flag). New interaction/state/narration patterns still get proven in the chat lane first; when a feature could land in either lane, chat leads.
- Resilience rules in `docs/resilience.md` are mandatory: `parseOr` at every trust boundary, diagnostics over exceptions, degraded defaults over failed turns.
- `src/contracts` and `src/lib` are pure (no IO/env/db). Server modules import each other only through `index.ts` barrels. Components never import `server/*`. These boundaries are enforced by an ESLint `no-restricted-imports` rule (`eslint.config.mjs`) — a violation fails `pnpm lint`.
- Registries (attributes, meters, fact kinds, body locations) are the extension points — vocabulary changes are data edits in one file, never schema migrations.
- DB workflow: edit `src/server/db/schema.ts` → `pnpm db:generate` → review SQL in `drizzle/` → `pnpm db:migrate`. Never `drizzle-kit push`. The initial migration (`drizzle/0000_*.sql`) begins with `CREATE EXTENSION IF NOT EXISTS vector`, so `pnpm db:migrate` self-enables pgvector and works on a fresh database without `pnpm db:create` (drizzle-kit does not emit this line — preserve it when regenerating the baseline migration).
  - **Never fake a TTY to auto-answer `db:generate`'s interactive create-vs-rename prompt.** Wrappers like `yes "" | script -qec "pnpm db:generate" /dev/null` (any unbounded input generator — `yes`, `while true; echo` — piped into a PTY emulator like `script`/`expect`/`unbuffer`) run away to multi-GB RAM and trip the machine's OOM killer (see memory `machine-earlyoom-oom-tuning`). When drizzle can't tell a rename from a create+drop it blocks on an arrow-key prompt; that prompt means the schema diff is ambiguous and needs a **human decision** — stop and ask the user to run `pnpm db:generate` themselves (suggest the `!` prefix), don't try to push through it.
- Tests: `pnpm test` (pure), `pnpm test:int` / `pnpm test:engine` (need Postgres) — never run locally (see the Validation bullet). CI runs `test` on every code PR and `test:engine` when DB/API/engine surfaces change; the wider `test:int` suite currently has no CI job. Degradation tests assert fallback **and** diagnostic code.
- **UI testing runs against the Fly deploy — do NOT spin up a local Postgres + `pnpm dev` (port 3200) for UI work anymore.** Push the change you want to see to Fly first, then drive the public build. Deploys are **manual** (a `git push` ships nothing): `fly deploy -a vesper` builds the Dockerfile on Fly's remote builder, runs `pnpm db:migrate` against Neon, and cuts the Machine over; verify with `fly status -a vesper`. Then point Playwright / chrome-devtools at `https://vesper.fly.dev`. Save any screenshots you take into the untracked `screenshots/` folder at the repo root (gitignored) — never into the repo root or `docs/`. Full Fly runbook: `docs/deployment.md`. (Local `pnpm dev` still exists for non-UI code work, and the local Postgres remains for DB workflow scripts — this only retires the local server as the **UI-testing** surface.)
  - A console **React #418 hydration error** on every page right after a Fly deploy is a known artifact of the fresh deploy, not an app bug — it clears on its own within a few minutes. Don't chase it during post-deploy verification.

- Validation is **CI-only — NEVER run lint, typecheck, tests, or verify locally.** That means no `pnpm lint`, `pnpm lint:cycles`, `pnpm lint:authz`, `pnpm typecheck`, `pnpm test`, `pnpm test:int`, `pnpm test:engine`, `pnpm jscpd`, `pnpm eval:engine-gate1`, and never `pnpm verify` — local runs drive this RAM-constrained machine into earlyoom territory and crash desktop apps. **For code, configuration, dependency, or workflow changes, validate by opening a PR and letting GitHub CI (`.github/workflows/ci.yml`) run every applicable gate** — a classifier job scopes the work: lint, cycles/authz/typecheck/jscpd, pure tests, and the production build (heap-pinned to the Fly builder's 4 GB ceiling) run for any code change; engine tests against Postgres and the engine eval run when the paths they cover are touched; the aggregate **`verify`** check requires all applicable jobs to pass. Push the branch, open the PR, watch the checks (`gh pr checks <n> --watch`), and fix failures by reading the CI logs and pushing follow-up commits — a change isn't done until `verify` is green. **For documentation-only changes** (only Markdown files and/or files under `docs/`), CI isn't needed either: do not manually dispatch or rerun it (the PR workflow emits a lightweight successful `verify` result without installing dependencies); review the rendered Markdown, links, and internal consistency instead. To write compliant code the first time, know what CI enforces: type-aware lint at `--max-warnings 0` with agent guardrails (`eslint.config.mjs` — no `any`/unsafe, no floating promises, exhaustive `switch`, module boundaries, provider gateway `@openrouter` only in `src/server/ai`), circular-import detection via madge, and jscpd as the copy-paste regression gate (its CI log lists the offending clones). The pre-commit hook (husky + lint-staged) still lints staged files automatically at commit time — that's fine because it's scoped and cheap; just never invoke the gates by hand.
- Git: after each **major task** (a feature or chore), write a descriptive, conventional-style commit message (`feat:` / `chore:` / `docs:` …). **Code, configuration, dependency, or workflow changes reach `main` via a branch + PR** — the PR's `verify` check is the only CI these changes ever get (push CI does not run on `main`), so merge on green and never push code commits directly to `main`. Documentation-only changes are the exception: commit and push them straight to `main`. Minor bug fixes and small improvements don't need their own PR — fold them into the next major task's branch.
- Working docs (`docs/developer-notes/`) use a **topic-named** convention — filenames encode _what_, never _when_. Priority order lives only in `roadmap.md`, so resequencing work never renames a file (the old `phase-N` scheme baked order into filenames and forced churny renames; don't reintroduce it).
  - **Plans** are `<topic>.plan.md` (e.g. `scene-images.plan.md`); the matching design/decision detail is `<topic>.spec.md`, post-ship fixes are `<topic>.followups.md`, and finer detail is `<topic>.<subtopic>.md`. Same topic slug ⇒ they nest together in the editor and `grep <topic>` finds every pointer (a stable target that doesn't rot on resequencing).
  - **Oversized plan/spec pairs split into a hub + unit docs.** The engine docs are the model: one `engine.gateN.<slug>.md` per gate (future gates included; gate numbers are stable architectural identities, not the banned reorderable `phase-N`), `engine.spec.<cluster>.md` files carrying globally-numbered § ranges, and `engine.plan.md` / `engine.spec.md` remaining as thin index hubs so every existing link and "§N" citation still resolves. Convention detail: `docs/developer-notes/CLAUDE.md` §"Engine gate docs".
  - Every plan opens with a `Status:` line — **draft** (not settled / placeholder), **next** (queued), **active** (in progress), **shipped — <date>** (with a completion note naming leftovers and where they went), or **parked** — and then an **`Outcome:` line**: one sentence, `<A player | The owner | A developer> can <do something concrete> so that <observable consequence>.` It names a person (never a system), promises something observable (never "more robust/reliable/polished"), and uses no vocabulary a first-time reader wouldn't know. If you can't write it, the work isn't understood well enough to plan. The roadmap keeps its own prose hook per entry, but that hook must not contradict the plan's Outcome line. Non-plan docs carry a Status line saying what they are (`companion to …`, `detail for …`, `reference (audit run <date>)`, `closed — <verdict> <date>`) and no Outcome line. Full rules and templates: the `vesper-docs` skill.
  - `roadmap.md` is the single ordered index of plans by current priority (+ a "someday" bucket pointing at `deferred.plan.md`, and a **Shipped** history split out into the sibling `roadmap.shipped.md`). It is the source of truth for what to build next and what's been done — **consult it whenever starting major-feature work**, and **keep it current as part of that work** (an out-of-date roadmap is a bug).
    - **The `## To be Planned` section (above the priority lists) is the owner's intake — never add to it.** It holds raw feature/improvement ideas the product owner wrote for themselves; agents **must not** add, edit, or reword entries there. Only act on it **on request**: when asked to plan one of its items, create the new `<topic>.plan.md` (or fold the idea into an existing plan), add the corresponding line to `## Next`/`## Active` below, and **then remove the now-planned item from `## To be Planned`** in the same change. Don't promote items unprompted.
    - **Work the roadmap order.** Default to building the top of `## Next`. Sometimes something must be built out of order (an urgent fix, a fast one-off) — that's allowed, but it **still gets a roadmap line** (added to `## Next`/`## Active` before or as you start, never built invisibly). Nothing of consequence gets built without appearing here.
    - **On completion, always update the roadmap** in the same change: add the finished entry to the Shipped history — which now lives in the sibling **`roadmap.shipped.md`** (newest-first, terse — one line: bold title — plan link · spec — `— <date>` — a short hook; full detail stays in the plan, not the roadmap), set the plan's `Status:` to `shipped — <date>`, and drop it from `## Active`/`## Next` in `roadmap.md`. Partially-shipped work (e.g. one slice of many) gets a Shipped line for the slice **and** stays in Next for the remainder, each cross-referencing the other.
    - **Reordering is allowed but should be rare** — a one-line move (never a file rename), and only a deliberate reprioritization, not incidental churn. Don't silently reshuffle while doing unrelated work.
  - Open questions raised anywhere in a topic's docs are restated in that topic's **plan** under an `## Open questions` section, each linking to the detail; resolving one = remove it from the plan and record the ruling in the detail doc.
  - Unplanned-but-good ideas not yet promoted to a plan are parked in `deferred.plan.md` (the parking-lot anchor); supporting detail is `<topic>.deferred.md`. When an idea graduates it becomes a `<topic>.plan.md`, gets a `roadmap.md` line, and leaves `deferred.plan.md` (a one-line "graduated → …" tombstone is fine).
  - **Archiving shipped docs → `finished/` (part of ship close-out; only `roadmap.md` repoints).** Once a plan's `Status:` is `shipped`, `git mv` its `<topic>.plan.md` / `.spec.md` (and any `<topic>.*` detail docs) into `docs/developer-notes/finished/` in the same change — an un-archived shipped plan is folder rot (rule detail: `docs/developer-notes/CLAUDE.md` §"Ship close-out"). When you do, **`roadmap.md` MUST be updated to link the new `finished/…` path** — it is the always-current index and must never carry a broken link. Every OTHER inbound link (sibling plans/specs, detail docs) is **left pointing at the old path — do not repoint them, and don't fix the moved doc's own outbound links either.** Repointing those is churn with little payoff: shipped docs are rarely reopened, so their stale links don't matter, and `grep <topic>` still finds both the moved file and its referrers. (This is the deliberate exception to the docs/README.md "repoint active inbound links" rule, which still applies to **live** system docs.) Moving plan+spec together keeps their mutual relative links resolving.
  - **Legacy `phase-N` docs** (`phase-N-plan.md`, `*.phaseN.md`, `followups.phaseN.md`) are the historical record of already-run phases — left as-is, not renamed. New work never uses phase numbers.
- This folder (the repo root) is its own pnpm installation root — `pnpm-workspace.yaml` pins it so pnpm never resolves a parent directory's workspace metadata. Run all pnpm commands from here, never from a parent directory.
