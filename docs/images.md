# Images

`src/server/images/` — full image suite: avatar generation, Venice reference editing (identity-locked portrait variants), and in-session scene images. All assets are rows in the `images` table with files under `data/` — one registry, one serving route, one lifecycle. (The old app had three parallel ad-hoc systems; don't recreate that.)

## Asset registry

- File path: `data/images/<ownerId>/<imageId>.webp` (always webp; converted on save). The `images` row carries `kind`, entity linkage, `prompt`, `source_image_id` (edit lineage), `status` (`pending`/`ready`/`failed`), `meta` (model, dimensions, timings).
- **Row before file**: insert the row as `pending` → write `<imageId>.pending.webp` → fsync → rename → update row to `ready`. Every file on disk is always explained by a row; a crash leaves a `pending`/`failed` row, never a mystery file.
- Serving: `GET /api/images/:id/file` (immutable cache headers — content never changes for an id).
- Deleting an entity nulls its `image_id` references and queues file deletion. An idempotent `image_sweep` job (on-demand + periodic) reconciles rows↔files both directions, logging orphans as warnings.
- Failed generations show a "regenerate" affordance (same prompt + parameters re-queued); `scene_image` jobs are idempotent per (session, turn, prompt).

## Pipelines

### Avatar generation (text → image)
Prompt built from the character's resolved attributes, **grouped by body region into label-free caption clauses and ordered so non-human morphology leads** (`Horns: …; Wings: …; Tail: …`, then skin, build, hair, eyes, face, style — scene-images.plan.md A+B+C). SDXL-family models (e.g. Lustify) front-load attention and parse grouped caption/tag phrasing far better than a flat `Label: value` metadata wall, so leading with the creature — and dropping the per-field label nouns (`Eye color: violet; Eye shape: almond` → `Eyes: violet, almond`) — stops the "human wearing fake wings" failure. Identity (gender + apparent age, plus **ethnicity** from `identity.heritage` appended after a comma) folds into the **subject line** as one phrase (`Subject: <name> — a young adult female succubus, Latina`); for **non-human** casts the species **label** is the noun there, via `speciesLabelPhrase` — the authored generic `appearance` description is deliberately **omitted** (the feature attributes already carry the morphology; re-enable via `speciesAppearancePhrase`), and `human` adds nothing. Ethnicity stays a comma-appended descriptor (distinct from the species noun) so "Latina succubus" reads right. Plus style (`realistic`/`stylized`) and the **default outfit**; the **bio is omitted** (no visual signal). Non-visual attributes (`kind: "sensory"` — voice, scent/taste) never reach an image prompt. The image prompt deliberately **omits the registry `promptHints`** — those are narrator/inference guidance (e.g. "state apparent age as an impression…"); an image model reads a hint's concrete example ("late thirties") as literal subject detail and anchored every face to it. promptHints still feed the narrator (`engine/scene.ts`); add one back to the image prompt only if testing shows it helps. Each outfit garment is phrased by its **description + sensory appearance, untruncated** — the name is only a fallback when a garment has no description; marked authoritative — without it the image model invents clothing that contradicts the saved wardrobe; an outfit lookup failure degrades to the attributes-only prompt with a warn diagnostic, `images.avatar.outfit_load_failed`. The outfit is **occlusion-filtered** first (`visibleAvatarOutfit`, same `resolveWardrobeVisibility` rule as scene images): layers fully hidden under opaque outer layers are omitted — mentioning the t-shirt under a closed abaya makes the model paint the abaya open — sheer-covered items become a vague hint, and coverage-less items (jewelry) stay. **Waist-up framing:** a garment whose coverage is entirely below the waist (pants, skirts, shoes — `belowWaistLocationIds` = `pelvis` + `legs`) is dropped, since handing the model trousers/footwear tempts a full-body shot against the "waist-up portrait" instruction; a garment that also covers the torso (dress, coat, abaya) stays. Scene images never apply this filter, so they keep full-body garments (followups.phase3.md §1). **The same waist-up cut applies to appearance attributes, not just garments:** `buildAvatarPrompt` drops every attribute whose `bodyLocationId` is below the waistline (`isBelowWaist` — feet, legs, hips, and all pelvic intimate anatomy), with **signature feature morphology exempt** (a `tail` roots at the pelvis but sweeps up into frame — `isFeatureAttributeCategory`). To own the garment gate and the attribute gate from one coverage source, `buildAvatarPrompt` takes the **raw wardrobe** (`loadDefaultWardrobe`, coverage included) and derives the visible outfit *and* region exposure itself, rather than receiving a pre-filtered outfit. **Low-value curation (scene-images "D"):** beyond the waist-up cut, `AVATAR_OMIT_ATTRIBUTES` drops fields that read poorly in a head-and-shoulders still and only dilute a limited-adherence SDXL model — `movement.*` (motion, invisible in a still), `build.height` (no reference to scale against), `skin.undertone`/`skin.texture`/`shoulders.slope`/`neck.*`/`brows.*` (sub-perceptible), `hands.*`/`arms.hair`/`ears.piercings` (out of frame or tiny), `lips.shape`, `horns.texture`, and **all `teeth.*`** ("sharp canines" makes the model render a ridiculous mouth). This list is **avatar-only** — scene images are full-body and source appearance from `characterAppearanceSummary`, which keeps the full set; a registry `imageValue` tag is the eventual home if the list grows. **Model switch:** the portrait studio offers a set of **uncensored Venice text-to-image models** (`veniceGenerateImage` via `veniceT2IModelId`) — `qwen` (the default, `qwen-image-2`, `VENICE_IMAGE_MODEL`-overridable), plus `lustify` / `chroma` / `illustrious` / `turbo` for cost/style/speed diversity (scene-images.spec.md §5). The picker vocabulary + labels live in the pure `contracts/images/image-models.ts` (`avatarImageModels`) so client and server share one key set; the key→Venice-model-id mapping is server-side in `veniceT2IModelId`. "Uncensored" is `safe_mode` off, the codebase default; a missing `VENICE_API_KEY` fails the row with that message; aspect 3:4 for every model, and the generator used is recorded on `images.meta.model`. (Flux/OpenRouter was removed from the image stack 2026-06-19 — every lane is Venice/Qwen now; OpenRouter stays for text only.) **Intimate-anatomy gating (body-model spec Decision 3):** `buildAvatarPrompt` takes `allowIntimate`, which avatar generation now passes **unconditionally** (every avatar route is the sole uncensored Venice one). Intimate attributes are still **exposure-gated** by the shared `intimateAttrRendersExposed` predicate — the same rule the scene render uses via `intimateSceneAppearance`: a covered region is withheld, sensory scent/taste never render, and since the waist-up cut already drops everything pelvic the only intimate category that can surface is `breasts`, and only when the chest reads `bare`/`sheer`. A bra-covered character emits **no** intimate detail. Non-intimate **`chest.hair`** is likewise exposure-gated — stated only when the torso reads bare/sheer, never under clothing. (The `allowIntimate=false` path remains live for the moderation-prone scene composer — `characterAppearanceSummary` keeps it off — and is kept on the avatar builder as an extensible seam in case a future SFW model is onboarded.) (These two image paths diverged once — the avatar path skipped exposure gating and dumped every intimate attribute on the Qwen route, including covered regions and below-waist anatomy in a waist-up shot, because intimate attributes were added *after* the coverage filter was built. The shared predicate is the fix: keep any new intimate-image rule in `intimateAttrRendersExposed`, exercised by both `buildAvatarPrompt` and `intimateSceneAppearance` tests.) **Image-gen failures are classified, not swallowed:** `describeImageGenError` (`server/ai/errors.ts`) recovers a real upstream message from an error body — historically a Flux/BFL `"Sexual Content"` moderation verdict that arrived *after* OpenRouter committed an HTTP 200 (slow gen → keep-alive padding → the AI SDK's success-schema parse throws a generic `APICallError("Invalid JSON response")`). Flux is gone, but the helper stays generic and `classifyImageFailure` reuses it to bucket a failure as transient / content_rejection / other for the scene fallback ladder. Venice's own routes return plain error strings, so they flow through the plain-message branch. The scene **composer** runs on the moderation-prone gemini `TOOL_MODEL`, so `characterAppearanceSummary` keeps `allowIntimate: false` there. Scene images instead get explicit anatomy via `intimateSceneAppearance` — **exposure-gated** (a region surfaces only when `bare`/`sheer`; sensory scent/taste never render), carried through the plan (`SceneCharacterSpec.intimateAppearance`) and emitted by `buildSceneRenderPrompt` **only when `allowIntimate` is set**, which `renderResolvedScene` passes on the uncensored Venice/Qwen reference-edit routes (never the Qwen text-to-image fallback). Injected at render assembly, not via the composer LLM — so a scene shows explicit anatomy iff the character has it, the region is exposed, and the route is uncensored. Runs as an `avatar` job; the UI polls the image row status, and failed non-canonical avatar attempts stay in the Portrait history grid with `images.meta.error` visible. The studio also shows the **canonical avatar's prompt** in a read-only box (between the generation controls and the variant form), sourced from `images.prompt` and updated when a variant is promoted — null when there is no avatar or it is an uploaded image (`meta.source: "upload"`, which carries no generation prompt).

### Avatar upload (user-supplied image)
Instead of generating, the user can upload their own picture in the portrait studio. The crop dialog (`components/characters/avatar-upload-dialog.tsx`) loads the file client-side; if it isn't already 3:4 the user pans/zooms it inside a 3:4 crop window (pure geometry in `@/lib/images/crop`), then a canvas renders the framed region to a JPEG data URL. `POST /api/characters/:id/avatar/upload` decodes it, re-fits to the canonical `AVATAR_WIDTH × AVATAR_HEIGHT` (768×1024) with sharp `cover` + EXIF `rotate()` (defense in depth — the client already cropped), saves through the normal row-before-file path (`kind: "avatar"`, `meta.source: "upload"`), and **promotes it to the avatar** in one synchronous request — no model runs, so it works in demo mode and offline. The new id returns in the response; the studio refetches immediately rather than polling.

### Portrait variants (reference edit, Venice)
Pose / outfit / expression / setting variants of the canonical avatar via Venice `VENICE_IMAGE_EDIT_MODEL` (default `qwen-image-2-edit` via `veniceEditModelId()`, shared with scene images): single reference image + instruction, prefixed with the **identity lock** block (preserve face, hair, age, build — port the old `PORTRAIT_IDENTITY_LOCK` wording). Variants accumulate in the character's portrait studio; any variant can be promoted to canonical avatar. Venice constraint: single-reference edit only — re-roll from the canonical portrait rather than chaining edits (drift compounds).

### Scene images (in-session)
Trigger: every N turns (`session.scene.interval`, 0 = off), or when the director flags `imageMoment.worthIt`, or manually.

**Player POV (hard rule)**: every scene image is composed from the player's eyes — first-person POV. The player never appears (no body, no face, no hands), and the player's appearance/wardrobe is never fed to the composer or the render prompt. The render prompt restates the rule verbatim (`SCENE_POV_RULE`). **Do not phrase the player AS the camera** — wording like "the player is the camera" made image models paint hands gripping a camera into the foreground; the rule reads "through the player's own eyes … no hands or held objects in frame" instead (a literal "no camera" negative would only anchor the model on it).

Pipeline (a `scene_image` job):
1. **Scene composer** (`TOOL_MODEL`, `generateChecked`): its candidate subject pool is **every NPC co-located with the player** — camera location from session state via `activeLocationId`, never from prose — so an NPC in another room can never reach the composer (`buildSceneComposerContext` in `engine/pipeline.ts`). Each present NPC arrives with a **species phrase** (label + generic `appearance` for non-human casts, via `speciesAppearancePhrase` — surfaced in both the composer line and the render's textual character detail), activity/posture and an **occlusion-filtered** wardrobe (`resolveWardrobeVisibility`, same rule as avatars: hidden layers omitted entirely, sheer-covered items at most a vague hint, coverage-less items kept) — visible garments phrased by description + appearance like the avatar, and **no waist-up filter** here so below-the-waist clothing reaches full-body scene shots. The same phrasing feeds both the composer prompt and the final render prompt. The composer also gets the location description/ambient, the session clock's daylight band for lighting, the director's scene summary, and the **last 2 turns' narration** (budgeted excerpts, newest largest). It designates ONE focal character from the pool — or none: an empty room composes a **location-only POV shot**, a legitimate output, not an error — plus which other present NPCs are in frame. The output is clamped server-side (`resolveScenePlan`): a focal name not in the room is replaced by a present NPC (`images.scene_composer.focal_clamped`), invented "others" are dropped (`images.scene_composer.absent_character_dropped`), and every character's outfit phrase is forced from wardrobe state — prose lies.
   - **Bare-region phrasing** (`exposedRegions` + `formatExposure`): listing only worn garments isn't enough — image models default every subject to fully clothed, so a removed top never shows. From each NPC's coverage we classify torso (`chest`), lower body (`pelvis`/groin·hips), legs (`thighs`), and feet — `covered` / `sheer` / `bare` — and inject explicit phrasing ("topless, bare chest", "bare below the waist", "bare legs", "barefoot", or a single "fully nude" when torso+pelvis+legs are all bare). Session item state is authoritative: if a present NPC has no worn clothing items, `exposedRegions([])` is the current outfit state and the render prompt says they are nude rather than keeping a clothed reference avatar. **head/hands are deliberately omitted** (bare there is the universal default and would fire on everyone); **feet are included by choice** — and since pants stop at `ankles`, an NPC with no modelled footwear reads barefoot.
2. **Render**: image generation is **Venice/Qwen end-to-end** (Flux/OpenRouter removed from the image stack 2026-06-19). References are always the **session participant's spawn-snapshot avatar** (`findParticipantAvatar` reads `session_participants.avatarImageId` only) — never the live library character portrait, since a session is frozen at spawn (re-snapshot only on restart); a library avatar changed mid-session therefore can't leak a different character into scene images. **Two reference modes, a per-session toggle** (`SceneGenState.referenceMode`, set on the Scene tab via `POST /api/sessions/:id/scene {action:"setReferenceMode"}`): **single** (default) anchors on ONE avatar (the focal's when ready, else the first present NPC with a ready avatar — `images.scene_render.reference_fallback`, info — the focal then described textually); **multi** gathers every present character's avatar in plan order **plus the active location's library image** and feeds up to 3 (`findSceneAnchors` + `loadLocationImage`; characters prioritised, location dropped first past the cap) to Venice `/image/multi-edit`, identity-locking each. Either way the other/overflow characters are described textually (appearance summary + state-forced outfit + action). The prompt asserts coverage state both ways — listed garments **and** bare regions — and closes with "depict only the clothing described … add no garment that is not listed", so the edit model can't re-paint a shed garment back onto the (fully-dressed) reference avatar. **Venice caps the edit prompt at 1500 chars** (`VENICE_RENDER_PROMPT_LIMIT`); untruncated garment descriptions blow that easily, so on **both** Venice edit paths (single + multi) `buildSceneRenderPrompt` progressively excerpts the outfit + setting text until it fits (word-boundary hard clamp as a final net) — identity lock, POV rule, pose, and bare-region phrasing are never dropped. Text-to-image (`venice_generate`, Qwen) is unbudgeted. **Provider routing & fallback ladder** (scene-images.spec.md §4/§8.3): the inline if-branches are gone — `renderSceneImage` builds a `SceneVisualReference[]` (the featured characters + location, with each available avatar's image + the location image + provenance attached) plus a `referenceBuffers` map (`imageId` → bytes), and `routeSceneProviders` picks an ordered chain from the capability registry `IMAGE_PROVIDERS` (`server/ai/image-providers.ts`, a typed code registry, not a DB table): multi-reference edit (`venice_multi_edit`, mode `multi`, when ≥2 reference images exist) → single-reference edit (`venice_edit`, when ≥1 anchor image) → Qwen text-to-image (`venice_generate`) → demo monogram. The caller's **`mode`** (`single`|`multi`, threaded `renderResolvedScene` → `routeSceneProviders`) only prepends the multi rung; it never blocks a render — `multi` degrades to the single ladder when fewer than two reference images are available. Character-chat scenes are always single-reference (one subject, no location image; the old Flux/Qwen picker was removed). The executor walks the chain with a **reason-keyed retry** — a **transient** failure (timeout/5xx/429, classified via `classifyImageFailure` reusing `describeImageGenError`) retries once on the same provider; a **content rejection** (moderation) never retries and drops to the next rung. Each provider gets its **own** prompt (single-edit, multi-edit, and text-to-image are distinct builders), so a text-to-image fallback never carries the identity-lock block (`allowIntimate` rides the image refs' `allowForIntimate` — for multi, every featured character ref must clear it; permissive today; the deferred uploaded-avatar guard, spec §3, flips it). Every downgrade logs `images.scene_render.provider_fallback` (info, `{from,to,reason}` — including the upstream Venice error message); a chain where every rung failed transiently logs `images.scene_render.service_outage` (warn). These diagnostics were long **black-holed** — no caller threaded a `DiagnosticSink`, so an identity-locked edit silently degrading to text-to-image (the character no longer resembling its reference avatar) left no trace; `renderResolvedScene` now tees them into a `DiagnosticCollector` and **drains it to the server log** (`drainSceneDiagnostics`, `images.scene_render` scope) on every render, staying quiet on the success path (which pushes nothing). This is strictly more resilient than before — a Venice failure used to mark the row failed; it now degrades down the ladder.
   - **Subject body reveal** (`imageReveal` tag, docs/contracts/attributes.md): the identity reference is a **waist-up** portrait, so it locks the face and upper body but underspecifies the figure below it. `buildSceneRenderPrompt` therefore supplements the identity-locked subject with a body line built from attributes tagged `imageReveal`: `"shape"` (silhouette that reads *through* clothing — breast size/shape, waist, hips, leg build/length, foot size) is described **always**; `"skin"` (surface detail — nipples, leg hair, toenails, foot arch) only when its region reads **bare/sheer**. Split by sensitivity via `sceneRevealAppearance(…, {intimate})`: the SFW lower-body half (`Body (below the portrait's framing): …`) rides every route; the intimate half (breast silhouette always, nipples/anatomy when exposed) rides only the uncensored route, exactly like the existing intimate phrase. Untagged intimate anatomy (vulva/penis) keeps the plain exposure gate, so nothing is lost. **Today this is wired on the character-chat scene path only** (`images/character-scene.ts`, the iteration ground for image-prompt tuning — its outfit + exposure now come from the character-chat **scenario modal**'s free-text `outfit` and `outfit_exposed` toggle rather than `profile.defaultOutfit`, since the chat has no equippable wardrobe; see [developer-notes/character-chat-scenario.plan.md](developer-notes/character-chat-scenario.plan.md)); avatars and in-session scenes keep strict exposure gating until the tag is adopted there. Tuning which fields reach the model — or flipping one between shape/skin — is a one-line registry edit on the attribute.
3. Result attaches to the session gallery (`images.session_id`). `/sessions/:id/status` reports the gen state plus `sceneGen.latestImageId` and `sceneGen.gallery` (ready scene images, pre-restart included, capped at 24; each entry carries its generation `prompt` for the **dev-only lightbox prompt panel**, docs/ui.md) — the gallery is DB-backed, so an in-flight render survives page refreshes and resurfaces there when it completes. The status route also self-heals an orphaned `generating` state (no live `scene_image` job → `failed`) so a dead runner never leaves a forever-spinner.

**Scene references (`image_references` join table):** at render, the scene records what it features — the focal + other in-frame characters resolved to their library `characterId` (`resolveSceneCharacterRefs`), the active location, and the identity anchor's avatar (with provenance) — as **one row per reference** in the `image_references` table (`recordImageReferences`), the **authoritative, queryable** record (docs/database.md). Columns: `kind` (`character`/`location`, with `style`/`pose`/`layout` reserved for multi-reference providers), `entity_id` (library id; null for non-entity roles), `role`, `source` (`generated`/`uploaded`/`composite`/`entity`; null = unknown), `image_id` (the asset actually fed to a provider; null when textual-only), `name`. FK-cascade on the scene image, so every delete path drops the rows automatically. This **replaced** `images.meta.references` (a one-time idempotent `scripts/backfill-image-references.ts` copied existing scenes over so they keep their facets); the contract split is `SceneVisualReference` (the render-input superset) vs `SceneReference` (the Gallery DTO the table projects to). It is still **forward-only** (older scenes that pre-date the backfill carry none) and is the seam a future multi-reference image model consumes, even though today's render still anchors on the single avatar above. The cross-session **Gallery** (`/gallery` · `GET /api/gallery` · [ui.md](ui.md)) lists every owner's **ready** scene image from two sources: **in-session** scenes across **still-existing** sessions (inner-join on `sessions`; deleting a session hard-deletes its scenes via `deleteSessionImages`, so there are no orphans), and **sessionless character-chat** scenes (`entityKind:"character"`, no `sessionId` — inner-joined to `characters` so a deleted character drops them too; see [developer-notes/character-chat.plan.md](developer-notes/finished/character-chat.plan.md)). Session scenes come first (grouped by session), then character-chat scenes under a trailing **"Character chats"** group. Filtered by world (session → world) and by character — the `character` refs sourced server-side from `image_references`, not `meta`. A scene is deletable from the grid — `DELETE /api/gallery/:id` → `deleteOwnedImage` (the single-asset, owner-scoped, `kind: "scene"`-guarded hard-delete: drop the row, unlink the file, sweep reconciles a straggler; the join rows cascade). A **Delete all** button beside the filters clears everything the active filter shows — `POST /api/gallery/delete {ids}` → `deleteOwnedImages` (the bulk counterpart: same owner-scope + `kind: "scene"` guard, one `IN (…)` delete, files unlinked best-effort). The client sends the ids it's currently showing, so "all worlds / all characters" deletes the whole gallery while a per-world or per-character filter deletes only that slice; a confirm dialog names the count and scope first. It's a clean 100% delete: the cross-session gallery *and* each session's scene gallery (`/sessions/:id/status`) are both derived live from the `images` table — there's no cached image id — so the scene leaves every view at once.

Failures mark the job + image row `failed` with the error; the session is never blocked by image work.

### Entity images (items & locations)
Library items and locations each carry one image (their `imageId` column), generated from the entity's own fields — no character-style variants, no upload, no gallery. `generateEntityImage({ entityKind, entityId, userId })` (`server/images/entity.ts`) builds the prompt, creates a `kind: "entity"` asset, generates (demo monogram fallback), and on success sets the row's `imageId` and **reclaims every other image for that entity** (a regenerate replaces the old one — single image per entity, no orphans). Prompt builders (`prompts.ts`): `buildItemImagePrompt` is a catalog product shot (clothing on a ghost mannequin, objects isolated on a seamless surface; aspect 1:1); `buildLocationImagePrompt` is an establishing shot whose type follows the location's **scale** — `open`/`expanse` → outdoor landscape, otherwise an architectural interior (aspect 3:2), always empty (no people). Triggered by `POST /api/{items,locations}/:id/image` as a background `entity_image` job (survives navigation); the editor's **Image** tab polls `GET /api/{items,locations}/:id/image` (latest row) until it leaves `pending`, shows the result with click-to-enlarge, and offers Regenerate. Entity deletion already drops these via `deleteEntityImages`. The library pages also carry a **Generate images** button: `POST /api/{items,locations}/images` takes the ids the client sends (those visible under the active type/search filter — so the Items library's All/Clothing/Object/Container buckets scope the batch), intersects them with the owner's still-missing entities (`missingEntityImageIds`), and runs `generateEntityImagesBatch` — parallel batches of `ENTITY_IMAGE_BATCH_SIZE` (5), one failure never aborting the rest — in a background job; the grid polls so images appear as they land. The button opens a confirm dialog naming how many images will be generated; entities that already have an image are skipped.

**New-world auto-generation:** saving a new world (the create routes — `POST /api/worlds/from-draft` and `POST /api/worlds`) fires `queueWorldImageGeneration`, a single background job that backfills every still-missing image the world references — cast avatars (`generateAvatarsBatch`), plus item and location images (`generateEntityImagesBatch`) — all in parallel batches of 5. It generates **only where the image is null**, so a world that reuses library entities keeps their existing images (and a reused entity that never had one still gets filled). It runs from the route, not from `createWorld`, so direct-call tests don't spawn image work; failures are logged, never surfaced to the save. The author can navigate away — images load into the cards as they finish.

## Demo mode

No keys → SVG monogram placeholder (deterministic gradient from the entity name) saved through the same registry path, flagged `meta.demo: true`. Every pipeline is exercisable in CI.

## Adding a pipeline

New generation kind = new `images.kind` value + a job type + a builder in `server/images/`. Use `generateChecked` for any prompt-composition step and the atomic-write helper for files. Update this doc.
