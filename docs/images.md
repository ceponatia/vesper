# Images

`src/server/images/` — full image suite: avatar generation, Venice reference editing (identity-locked portrait variants), and character-chat scene images. All assets are rows in the `images` table with files under `data/` — one registry, one serving route, one lifecycle. (The old app had three parallel ad-hoc systems; don't recreate that.)

## Asset registry

- File path: `data/images/<ownerId>/<imageId>.webp` (always webp; converted on save). The `images` row carries `kind`, entity linkage, `prompt`, `source_image_id` (edit lineage), `status` (`pending`/`ready`/`failed`), `meta` (model, dimensions, timings).
- **Path containment:** `DATA_ROOT` is resolved to an absolute canonical root before use. Every stored path, write target, delete, copy, and sweep entry is resolved through the same strict containment seam; traversal, absolute paths, sibling-prefix tricks, backslashes, and any existing symlink component are rejected. Full image rows must match `images/<ownerId>/<imageId>.webp` exactly. `db:migrate` repairs legacy path values to that shape and installs the `images_path_canonical` CHECK constraint, so future database writes cannot store another path.
- **Row before file**: insert the row as `pending` → write `<imageId>.pending.webp` → fsync → rename → update row to `ready`. Every file on disk is always explained by a row; a crash leaves a `pending`/`failed` row, never a mystery file. The temporary file is opened with `O_NOFOLLOW` and both temporary and final paths are revalidated beneath `DATA_ROOT`.
- Serving: `GET /api/images/:id/file` (immutable cache headers — content never changes for an id). **The gate is owner-first:** you always get your own images; a cross-owner read is allowed only when the image's `entity_kind`/`entity_id` name a **public** shareable entity **owned by the same account as the image** (`isPublicEntityImage(entityKind, entityId, row.ownerId)`). The ownership half of that predicate is what makes it safe: the entity linkage is polymorphic metadata with no FK, so without it the check reads "some public row has this id" and any path that ever let a user write those columns would publish their own private asset by naming someone else's public character (security-authz.plan.md slice 3). `Cache-Control` follows the same split — `public` for public-entity images, `private` for owner-only, so a shared cache can never serve one user's asset to another.
- Image rows returned **beside a public entity** (the character detail response's portrait strip) are projected to `{ id, kind, entityKind, entityId, createdAt }` — never `path` (storage layout) or `prompt` (prompts embed authored + chat text, which is why `deleteChat` scrubs them). The portrait studio's full rows come from the owner-strict `GET /api/characters/:id/portraits`.
- Deleting an entity **hard-deletes** its owned `images` rows and unlinks the files immediately (best-effort `fs.unlink`, not a queued job — `deleteEntityImages`). Only a **chat** deletion differs: it nulls `images.chat_id` (`SET NULL`) and deliberately keeps the asset (it survives in the Gallery). An idempotent `image_sweep` job (on-demand + periodic) reconciles rows↔files both directions, logging orphans as warnings.
- Failed generations show a "regenerate" affordance (same prompt + parameters re-queued). Chat scene renders are deduped to **one live render per chat** — `queueChatScene` short-circuits when a `queued`/`running` `chat_scene_image` job already exists for the conversation (the guard is keyed on chat + type + status, not on turn number or prompt text).

## Pipelines

### Avatar generation (text → image)
Prompt built from the character's resolved attributes, **grouped by body region into label-free caption clauses and ordered so non-human morphology leads** (`Horns: …; Wings: …; Tail: …`, then skin, build, hair, eyes, face, style — scene-images.plan.md A+B+C). SDXL-family models (e.g. Lustify) front-load attention and parse grouped caption/tag phrasing far better than a flat `Label: value` metadata wall, so leading with the creature — and dropping the per-field label nouns (`Eye color: violet; Eye shape: almond` → `Eyes: violet, almond`) — stops the "human wearing fake wings" failure. Identity (gender + apparent age, plus **ethnicity** from `identity.heritage` appended after a comma) folds into the **subject line** as one phrase (`Subject: <name> — a young adult female succubus, Latina`). **Apparent age is a portrait-studio concept** — only `buildAvatarPrompt` (and the portrait-variant `PORTRAIT_IDENTITY_LOCK`) emit it. Scene images deliberately **omit** it (`characterAppearanceSummary` skips `identity.apparent_age`) so they lean on the character's avatar as the source of how old they read, rather than fighting it with a text band; and the **narrator** sees the separate real `age` field, not apparent age (the two need not align — a 500-year-old who looks thirty). for **non-human** casts the species **label** is the noun there, via `speciesLabelPhrase` — the authored generic `appearance` description is deliberately **omitted** (the feature attributes already carry the morphology; re-enable via `speciesAppearancePhrase`), and `human` adds nothing. Ethnicity stays a comma-appended descriptor (distinct from the species noun) so "Latina succubus" reads right. Plus style (`realistic`/`stylized`) and the **default outfit**; the **bio is omitted** (no visual signal). Non-visual attributes (`kind: "sensory"` — voice, scent/taste) never reach an image prompt. The image prompt deliberately **omits the registry `promptHints`** — those are narrator/inference guidance (e.g. "state apparent age as an impression…"); an image model reads a hint's concrete example ("late thirties") as literal subject detail and anchored every face to it. promptHints still feed the narrator (`engine/scene.ts`); add one back to the image prompt only if testing shows it helps. Each outfit garment is phrased by its **description + sensory appearance, untruncated** — the name is only a fallback when a garment has no description — and an accessory's **subtype label leads the phrase** (`nose ring: thin gold hoop`, `formatGarment`; skipped when the text already names the type): jewelry names alone gave the model nothing to place the piece (face-jewelry plan, [contracts/items.md](contracts/items.md) §Clothing subtypes; the same phrasing feeds scene wardrobe lines and the narrator's Visible-wardrobe block). Marked authoritative — without it the image model invents clothing that contradicts the saved wardrobe; an outfit lookup failure degrades to the attributes-only prompt with a warn diagnostic, `images.avatar.outfit_load_failed`. The outfit is **occlusion-filtered** first (`visibleAvatarOutfit`, same `resolveWardrobeVisibility` rule as scene images): layers fully hidden under opaque outer layers are omitted — mentioning the t-shirt under a closed abaya makes the model paint the abaya open — sheer-covered items become a vague hint, and coverage-less items (jewelry) stay. **Waist-up framing:** a garment whose coverage is entirely below the waist (pants, skirts, shoes — `belowWaistLocationIds` = `pelvis` + `legs`) is dropped, since handing the model trousers/footwear tempts a full-body shot against the "waist-up portrait" instruction; a garment that also covers the torso (dress, coat, abaya) stays. Scene images never apply this filter, so they keep full-body garments (followups.phase3.md §1). **The same waist-up cut applies to appearance attributes, not just garments:** `buildAvatarPrompt` drops every attribute whose `bodyLocationId` is below the waistline (`isBelowWaist` — feet, legs, hips, and all pelvic intimate anatomy), with **signature feature morphology exempt** (a `tail` roots at the pelvis but sweeps up into frame — `isFeatureAttributeCategory`). To own the garment gate and the attribute gate from one coverage source, `buildAvatarPrompt` takes the **raw wardrobe** (`loadDefaultWardrobe`, coverage included) and derives the visible outfit *and* region exposure itself, rather than receiving a pre-filtered outfit. **Low-value curation (scene-images "D"):** beyond the waist-up cut, `AVATAR_OMIT_ATTRIBUTES` drops fields that read poorly in a head-and-shoulders still and only dilute a limited-adherence SDXL model — `movement.*` (motion, invisible in a still), `build.height` (no reference to scale against), `skin.undertone`/`skin.texture`/`shoulders.slope`/`neck.*`/`brows.*` (sub-perceptible), `hands.*`/`arms.hair` (out of frame or tiny; `ears.piercings` rejoined the prompt with the face-jewelry work — piercings are first-class visual detail now, alongside the new `nose.*`/`lips.piercings` attributes), `lips.shape`, `horns.texture`, and **all `teeth.*`** ("sharp canines" makes the model render a ridiculous mouth). This list is **avatar-only** — scene images are full-body and source appearance from `characterAppearanceSummary`, which keeps the full set; a registry `imageValue` tag is the eventual home if the list grows. **Model switch:** the portrait studio offers a set of **uncensored Venice text-to-image models** (`veniceGenerateImage` via `veniceT2IModelId()`) — `chroma` (the default since the 2026-07-10 owner ruling — photoreal), plus `qwen` (the former default, `qwen-image-2`, `VENICE_IMAGE_MODEL`-overridable) / `lustify` / `illustrious` / `turbo` for cost/style/speed diversity (scene-images.spec.md §5). `DEFAULT_AVATAR_IMAGE_MODEL` also drives the scene ladder's text-to-image rung via `veniceSceneImageModelId` (below), so the two lanes' defaults can't drift. The picker vocabulary + labels live in the pure `contracts/images/image-models.ts` (`avatarImageModels`) so client and server share one key set; the key→Venice-model-id mapping is server-side in `veniceT2IModelId`. "Uncensored" is `safe_mode` off, the codebase default; a missing `VENICE_API_KEY` fails the row with that message; aspect 3:4 for every model, and the generator used is recorded on `images.meta.model`. (Flux/OpenRouter was removed from the image stack 2026-06-19 — every lane is Venice/Qwen now; OpenRouter stays for text only.) **Intimate-anatomy gating (2026-07-08, supersedes body-model spec Decision 3):** the portrait studio is **intimate-free by rule** — `buildAvatarPrompt` drops every intimate-category attribute unconditionally (the `allowIntimate` parameter is gone), whatever the default outfit exposes. The waist-up cut already removed everything pelvic; this closes the remaining seam where a bare-chested default outfit put `breasts.*` detail into the avatar prompt. Intimate anatomy is **scene-render-only**: session scenes gate it by wardrobe exposure (`intimateAttrRendersExposed` via `intimateSceneAppearance`), character-chat scenes by the scenario modal's "Reveal intimate anatomy" toggle (`outfit_exposed`). Non-intimate **`chest.hair`** stays exposure-gated in the avatar — stated only when the torso reads bare/sheer, never under clothing. (`characterAppearanceSummary` keeps `allowIntimate: false` for the moderation-prone scene composer; keep any new intimate-image rule in `intimateAttrRendersExposed`, exercised by the `intimateSceneAppearance` tests.) **Image-gen failures are classified, not swallowed:** `describeImageGenError` (`server/ai/errors.ts`) recovers a real upstream message from an error body — historically a Flux/BFL `"Sexual Content"` moderation verdict that arrived *after* OpenRouter committed an HTTP 200 (slow gen → keep-alive padding → the AI SDK's success-schema parse throws a generic `APICallError("Invalid JSON response")`). Flux is gone, but the helper stays generic and `classifyImageFailure` reuses it to bucket a failure as transient / content_rejection / other for the scene fallback ladder. Venice's own routes return plain error strings, so they flow through the plain-message branch. The scene **composer** runs on the moderation-prone tool-model default (`toolModelId`), so `characterAppearanceSummary` keeps `allowIntimate: false` there. Scene images instead get explicit anatomy via `intimateSceneAppearance` — **exposure-gated** (a region surfaces only when `bare`/`sheer`; sensory scent/taste never render), carried through the plan (`SceneCharacterSpec.intimateAppearance`) and emitted by `buildSceneRenderPrompt` **only when `allowIntimate` is set**, which `renderResolvedScene` passes on the uncensored Venice/Qwen reference-edit routes (never the Qwen text-to-image fallback). Injected at render assembly, not via the composer LLM — so a scene shows explicit anatomy iff the character has it, the region is exposed, and the route is uncensored. Runs as an `avatar` job; the UI polls the image row status, and failed non-canonical avatar attempts stay in the Portrait history grid with `images.meta.error` visible. The studio also shows the **canonical avatar's prompt** in a read-only box (between the generation controls and the variant form), sourced from `images.prompt` and updated when a variant is promoted — null when there is no avatar or it is an uploaded image (`meta.source: "upload"`, which carries no generation prompt).

### Avatar upload (user-supplied image)
Instead of generating, the user can upload their own picture in the portrait studio. The crop dialog (`components/characters/avatar-upload-dialog.tsx`) loads the file client-side; if it isn't already 3:4 the user pans/zooms it inside a 3:4 crop window (pure geometry in `@/lib/images/crop`), then a canvas renders the framed region to a JPEG data URL. `POST /api/characters/:id/avatar/upload` decodes it, re-fits to the canonical `AVATAR_WIDTH × AVATAR_HEIGHT` (768×1024) with sharp `cover` + EXIF `rotate()` (defense in depth — the client already cropped), saves through the normal row-before-file path (`kind: "avatar"`, `meta.source: "upload"`), and **promotes it to the avatar** in one synchronous request — no model runs, so it works in demo mode and offline. The new id returns in the response; the studio refetches immediately rather than polling.

### Portrait variants (reference edit, Venice)
Pose / outfit / expression / setting variants of the canonical avatar via Venice `VENICE_IMAGE_EDIT_MODEL` (default `qwen-image-2-edit` via `veniceEditModelId()`, shared with scene images): single reference image + instruction, prefixed with the **identity lock** block (preserve face, hair, age, build — port the old `PORTRAIT_IDENTITY_LOCK` wording). Variants accumulate in the character's portrait studio; any variant can be promoted to canonical avatar. **Promotion is owner-strict inside the service** (`promoteVariant(characterId, imageId, ownerId)`): the route's `findOwnedCharacter` gate stays as defense in depth, but the service re-matches BOTH the character row and the image row on `ownerId` in the same query as the id before writing, and only then checks the `entity_kind`/`entity_id` link and `status: ready`. Ownership is never inferred from the polymorphic entity linkage — repointing an owned image at someone else's public character buys nothing (same trust boundary as the file-serving gate above; security-authz.plan.md §Follow-ups item 2). Rejections return `{ ok: false, error }` with a foreign row reported as a plain "not found" (no not-yours signal) and a `log.warn` diagnostic (`images.promote.*`). Venice constraint: single-reference edit only — re-roll from the canonical portrait rather than chaining edits (drift compounds).

### Scene images (character chat)
Trigger: every N turns (`SceneGenState.interval`, 0 = off), on a milestone/strong-reaction when the chat's `sceneAuto` is `"milestones"`, or manually. The render pipeline below is shared with avatars/portraits; the chat lane feeds it via `buildCharacterSceneContext` + `queueChatScene` (`images/character-scene.ts`).

**Player POV**: every scene image is composed from the player's eyes — first-person POV; the player's face and head are never in frame. **Do not phrase the player AS the camera** — wording like "the player is the camera" made image models paint hands gripping a camera into the foreground; the rule reads "through the player's own eyes … no hands or held objects in frame" instead (a literal "no camera" negative would only anchor the model on it).

**Embodied POV — chat lane only** (scene-pov-embodiment.plan.md): the player's absolute absence was a useful lie (the fiction constantly puts their hands on someone and the image couldn't show it), so the chat lane now lets the viewer's own body enter the foreground. `sceneFramingRule({parts, subjects})` returns `SCENE_POV_RULE` **byte-identical** with no parts and the embodied variant with them; `SceneComposerContext.embodiedViewer` is the opt-in and **only `buildCharacterSceneContext` sets it**, so the non-embodied variant stays the default (`sceneComposerSystem(false) === SCENE_COMPOSER_SYSTEM`, pinned).
