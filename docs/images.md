# Images

`src/server/images/` — full image suite: avatar generation, Venice reference editing (identity-locked portrait variants), and character-chat scene images. All assets are rows in the `images` table with files under `data/` — one registry, one serving route, one lifecycle. (The old app had three parallel ad-hoc systems; don't recreate that.)

## Asset registry

- File path: `data/images/<ownerId>/<imageId>.webp` (always webp; converted on save). The `images` row carries `kind`, entity linkage, `prompt`, `source_image_id` (edit lineage), `status` (`pending`/`ready`/`failed`), `meta` (model, dimensions, timings).
- **Row before file**: insert the row as `pending` → write `<imageId>.pending.webp` → fsync → rename → update row to `ready`. Every file on disk is always explained by a row; a crash leaves a `pending`/`failed` row, never a mystery file.
- Serving: `GET /api/images/:id/file` (immutable cache headers — content never changes for an id). **The gate is owner-first:** you always get your own images; a cross-owner read is allowed only when the image's `entity_kind`/`entity_id` name a **public** shareable entity **owned by the same account as the image** (`isPublicEntityImage(entityKind, entityId, row.ownerId)`). The ownership half of that predicate is what makes it safe: the entity linkage is polymorphic metadata with no FK, so without it the check reads "some public row has this id" and any path that ever let a user write those columns would publish their own private asset by naming someone else's public character (security-authz.plan.md slice 3). `Cache-Control` follows the same split — `public` for public-entity images, `private` for owner-only, so a shared cache can never serve one user's asset to another.
- Image rows returned **beside a public entity** (the character detail response's portrait strip) are projected to `{ id, kind, entityKind, entityId, createdAt }` — never `path` (storage layout) or `prompt` (prompts embed authored + chat text, which is why `deleteChat` scrubs them). The portrait studio's full rows come from the owner-strict `GET /api/characters/:id/portraits`.
- Deleting an entity **hard-deletes** its owned `images` rows and unlinks the files immediately (best-effort `fs.unlink`, not a queued job — `deleteEntityImages`). Only a **chat** deletion differs: it nulls `images.chat_id` (`SET NULL`) and deliberately keeps the asset (it survives in the Gallery). An idempotent `image_sweep` job (on-demand + periodic) reconciles rows↔files both directions, logging orphans as warnings.
- Failed generations show a "regenerate" affordance (same prompt + parameters re-queued). Chat scene renders are deduped to **one live render per chat** — `queueChatScene` short-circuits when a `queued`/`running` `chat_scene_image` job already exists for the conversation (the guard is keyed on chat + type + status, not on turn number or prompt text).

## Pipelines

### Avatar generation (text → image)
Prompt built from the character's resolved attributes, **grouped by body region into label-free caption clauses and ordered so non-human morphology leads** (`Horns: …; Wings: …; Tail: …`, then skin, build, hair, eyes, face, style — scene-images.plan.md A+B+C). SDXL-family models (e.g. Lustify) front-load attention and parse grouped caption/tag phrasing far better than a flat `Label: value` metadata wall, so leading with the creature — and dropping the per-field label nouns (`Eye color: violet; Eye shape: almond` → `Eyes: violet, almond`) — stops the "human wearing fake wings" failure. Identity (gender + apparent age, plus **ethnicity** from `identity.heritage` appended after a comma) folds into the **subject line** as one phrase (`Subject: <name> — a young adult female succubus, Latina`). **Apparent age is a portrait-studio concept** — only `buildAvatarPrompt` (and the portrait-variant `PORTRAIT_IDENTITY_LOCK`) emit it. Scene images deliberately **omit** it (`characterAppearanceSummary` skips `identity.apparent_age`) so they lean on the character's avatar as the source of how old they read, rather than fighting it with a text band; and the **narrator** sees the separate real `age` field, not apparent age (the two need not align — a 500-year-old who looks thirty). for **non-human** casts the species **label** is the noun there, via `speciesLabelPhrase` — the authored generic `appearance` description is deliberately **omitted** (the feature attributes already carry the morphology; re-enable via `speciesAppearancePhrase`), and `human` adds nothing. Ethnicity stays a comma-appended descriptor (distinct from the species noun) so "Latina succubus" reads right. Plus style (`realistic`/`stylized`) and the **default outfit**; the **bio is omitted** (no visual signal). Non-visual attributes (`kind: "sensory"` — voice, scent/taste) never reach an image prompt. The image prompt deliberately **omits the registry `promptHints`** — those are narrator/inference guidance (e.g. "state apparent age as an impression…"); an image model reads a hint's concrete example ("late thirties") as literal subject detail and anchored every face to it. promptHints still feed the narrator (`engine/scene.ts`); add one back to the image prompt only if testing shows it helps. Each outfit garment is phrased by its **description + sensory appearance, untruncated** — the name is only a fallback when a garment has no description — and an accessory's **subtype label leads the phrase** (`nose ring: thin gold hoop`, `formatGarment`; skipped when the text already names the type): jewelry names alone gave the model nothing to place the piece (face-jewelry plan, [contracts/items.md](contracts/items.md) §Clothing subtypes; the same phrasing feeds scene wardrobe lines and the narrator's Visible-wardrobe block). Marked authoritative — without it the image model invents clothing that contradicts the saved wardrobe; an outfit lookup failure degrades to the attributes-only prompt with a warn diagnostic, `images.avatar.outfit_load_failed`. The outfit is **occlusion-filtered** first (`visibleAvatarOutfit`, same `resolveWardrobeVisibility` rule as scene images): layers fully hidden under opaque outer layers are omitted — mentioning the t-shirt under a closed abaya makes the model paint the abaya open — sheer-covered items become a vague hint, and coverage-less items (jewelry) stay. **Waist-up framing:** a garment whose coverage is entirely below the waist (pants, skirts, shoes — `belowWaistLocationIds` = `pelvis` + `legs`) is dropped, since handing the model trousers/footwear tempts a full-body shot against the "waist-up portrait" instruction; a garment that also covers the torso (dress, coat, abaya) stays. Scene images never apply this filter, so they keep full-body garments (followups.phase3.md §1). **The same waist-up cut applies to appearance attributes, not just garments:** `buildAvatarPrompt` drops every attribute whose `bodyLocationId` is below the waistline (`isBelowWaist` — feet, legs, hips, and all pelvic intimate anatomy), with **signature feature morphology exempt** (a `tail` roots at the pelvis but sweeps up into frame — `isFeatureAttributeCategory`). To own the garment gate and the attribute gate from one coverage source, `buildAvatarPrompt` takes the **raw wardrobe** (`loadDefaultWardrobe`, coverage included) and derives the visible outfit *and* region exposure itself, rather than receiving a pre-filtered outfit. **Low-value curation (scene-images "D"):** beyond the waist-up cut, `AVATAR_OMIT_ATTRIBUTES` drops fields that read poorly in a head-and-shoulders still and only dilute a limited-adherence SDXL model — `movement.*` (motion, invisible in a still), `build.height` (no reference to scale against), `skin.undertone`/`skin.texture`/`shoulders.slope`/`neck.*`/`brows.*` (sub-perceptible), `hands.*`/`arms.hair` (out of frame or tiny; `ears.piercings` rejoined the prompt with the face-jewelry work — piercings are first-class visual detail now, alongside the new `nose.*`/`lips.piercings` attributes), `lips.shape`, `horns.texture`, and **all `teeth.*`** ("sharp canines" makes the model render a ridiculous mouth). This list is **avatar-only** — scene images are full-body and source appearance from `characterAppearanceSummary`, which keeps the full set; a registry `imageValue` tag is the eventual home if the list grows. **Model switch:** the portrait studio offers a set of **uncensored Venice text-to-image models** (`veniceGenerateImage` via `veniceT2IModelId`) — `chroma` (the default since the 2026-07-10 owner ruling — photoreal), plus `qwen` (the former default, `qwen-image-2`, `VENICE_IMAGE_MODEL`-overridable) / `lustify` / `illustrious` / `turbo` for cost/style/speed diversity (scene-images.spec.md §5). `DEFAULT_AVATAR_IMAGE_MODEL` also drives the scene ladder's text-to-image rung via `veniceSceneImageModelId` (below), so the two lanes' defaults can't drift. The picker vocabulary + labels live in the pure `contracts/images/image-models.ts` (`avatarImageModels`) so client and server share one key set; the key→Venice-model-id mapping is server-side in `veniceT2IModelId`. "Uncensored" is `safe_mode` off, the codebase default; a missing `VENICE_API_KEY` fails the row with that message; aspect 3:4 for every model, and the generator used is recorded on `images.meta.model`. (Flux/OpenRouter was removed from the image stack 2026-06-19 — every lane is Venice/Qwen now; OpenRouter stays for text only.) **Intimate-anatomy gating (2026-07-08, supersedes body-model spec Decision 3):** the portrait studio is **intimate-free by rule** — `buildAvatarPrompt` drops every intimate-category attribute unconditionally (the `allowIntimate` parameter is gone), whatever the default outfit exposes. The waist-up cut already removed everything pelvic; this closes the remaining seam where a bare-chested default outfit put `breasts.*` detail into the avatar prompt. Intimate anatomy is **scene-render-only**: session scenes gate it by wardrobe exposure (`intimateAttrRendersExposed` via `intimateSceneAppearance`), character-chat scenes by the scenario modal's "Reveal intimate anatomy" toggle (`outfit_exposed`). Non-intimate **`chest.hair`** stays exposure-gated in the avatar — stated only when the torso reads bare/sheer, never under clothing. (`characterAppearanceSummary` keeps `allowIntimate: false` for the moderation-prone scene composer; keep any new intimate-image rule in `intimateAttrRendersExposed`, exercised by the `intimateSceneAppearance` tests.) **Image-gen failures are classified, not swallowed:** `describeImageGenError` (`server/ai/errors.ts`) recovers a real upstream message from an error body — historically a Flux/BFL `"Sexual Content"` moderation verdict that arrived *after* OpenRouter committed an HTTP 200 (slow gen → keep-alive padding → the AI SDK's success-schema parse throws a generic `APICallError("Invalid JSON response")`). Flux is gone, but the helper stays generic and `classifyImageFailure` reuses it to bucket a failure as transient / content_rejection / other for the scene fallback ladder. Venice's own routes return plain error strings, so they flow through the plain-message branch. The scene **composer** runs on the moderation-prone tool-model default (`toolModelId`), so `characterAppearanceSummary` keeps `allowIntimate: false` there. Scene images instead get explicit anatomy via `intimateSceneAppearance` — **exposure-gated** (a region surfaces only when `bare`/`sheer`; sensory scent/taste never render), carried through the plan (`SceneCharacterSpec.intimateAppearance`) and emitted by `buildSceneRenderPrompt` **only when `allowIntimate` is set**, which `renderResolvedScene` passes on the uncensored Venice/Qwen reference-edit routes (never the Qwen text-to-image fallback). Injected at render assembly, not via the composer LLM — so a scene shows explicit anatomy iff the character has it, the region is exposed, and the route is uncensored. Runs as an `avatar` job; the UI polls the image row status, and failed non-canonical avatar attempts stay in the Portrait history grid with `images.meta.error` visible. The studio also shows the **canonical avatar's prompt** in a read-only box (between the generation controls and the variant form), sourced from `images.prompt` and updated when a variant is promoted — null when there is no avatar or it is an uploaded image (`meta.source: "upload"`, which carries no generation prompt).

### Avatar upload (user-supplied image)
Instead of generating, the user can upload their own picture in the portrait studio. The crop dialog (`components/characters/avatar-upload-dialog.tsx`) loads the file client-side; if it isn't already 3:4 the user pans/zooms it inside a 3:4 crop window (pure geometry in `@/lib/images/crop`), then a canvas renders the framed region to a JPEG data URL. `POST /api/characters/:id/avatar/upload` decodes it, re-fits to the canonical `AVATAR_WIDTH × AVATAR_HEIGHT` (768×1024) with sharp `cover` + EXIF `rotate()` (defense in depth — the client already cropped), saves through the normal row-before-file path (`kind: "avatar"`, `meta.source: "upload"`), and **promotes it to the avatar** in one synchronous request — no model runs, so it works in demo mode and offline. The new id returns in the response; the studio refetches immediately rather than polling.

### Portrait variants (reference edit, Venice)
Pose / outfit / expression / setting variants of the canonical avatar via Venice `VENICE_IMAGE_EDIT_MODEL` (default `qwen-image-2-edit` via `veniceEditModelId()`, shared with scene images): single reference image + instruction, prefixed with the **identity lock** block (preserve face, hair, age, build — port the old `PORTRAIT_IDENTITY_LOCK` wording). Variants accumulate in the character's portrait studio; any variant can be promoted to canonical avatar. Venice constraint: single-reference edit only — re-roll from the canonical portrait rather than chaining edits (drift compounds).

### Scene images (character chat)
Trigger: every N turns (`SceneGenState.interval`, 0 = off), on a milestone/strong-reaction when the chat's `sceneAuto` is `"milestones"`, or manually. The render pipeline below is shared with avatars/portraits; the chat lane feeds it via `buildCharacterSceneContext` + `queueChatScene` (`images/character-scene.ts`).

**Player POV**: every scene image is composed from the player's eyes — first-person POV; the player's face and head are never in frame. **Do not phrase the player AS the camera** — wording like "the player is the camera" made image models paint hands gripping a camera into the foreground; the rule reads "through the player's own eyes … no hands or held objects in frame" instead (a literal "no camera" negative would only anchor the model on it).

**Embodied POV — chat lane only** (scene-pov-embodiment.plan.md): the player's absolute absence was a useful lie (the fiction constantly puts their hands on someone and the image couldn't show it), so the chat lane now lets the viewer's own body enter the foreground. `sceneFramingRule({parts, subjects})` returns `SCENE_POV_RULE` **byte-identical** with no parts and the embodied variant with them; `SceneComposerContext.embodiedViewer` is the opt-in and **only `buildCharacterSceneContext` sets it**, so the non-embodied variant stays the default (`sceneComposerSystem(false) === SCENE_COMPOSER_SYSTEM`, pinned). What stops a limb becoming a third person is never a negative ("no man in frame" anchors on *man*, as "no camera" once did): it is **possessive binding** ("the viewer's own"), **frame geometry** (cropped by the edge, strongly foreshortened — a limb the frame cuts through can't be composed as someone standing there), and a **positive person-count assertion** derived from the featured list (the realistic-model analogue of booru `solo focus`). The vocabulary is a closed registry (`contracts/images/viewer-body.ts`), because the phrasing IS the feature. The composer proposes non-intimate parts only — it runs on the moderation-prone tool model with `allowIntimate: false`, so **intimate anatomy never touches it**, exactly as `intimateSceneAppearance` never has. `resolveViewerParts` is the gate — unknown id → route → coverage, with **missing coverage counting as covered** (default-shut) — and it runs **per-prompt** inside `buildSceneRenderPrompt`, since the ladder's rungs disagree about `allowIntimate`. Only anatomy is gated: a *clothed* torso in frame is a fine POV element. **The player's coverage is computed from their persona's worn items** ([character-chat/state.md](character-chat/state.md) §The player's wardrobe), never a manual flag — which is why that wardrobe has no `exposed` toggle at all.

Pipeline (a `scene_image` job):
1. **Scene composer** (`toolModelId`, `generateChecked`): its candidate subject pool is the **conversation's roster** — the scene/place comes from the chat's scene memory, never from prose (`buildCharacterSceneContext`). Each present character arrives with a **species phrase** (label + generic `appearance` for non-human casts, via `speciesAppearancePhrase` — surfaced in both the composer line and the render's textual character detail), activity/posture and an **occlusion-filtered** wardrobe (`resolveWardrobeVisibility`, same rule as avatars: hidden layers omitted entirely, sheer-covered items at most a vague hint, coverage-less items kept) — visible garments phrased by description + appearance like the avatar, and **no waist-up filter** here so below-the-waist clothing reaches full-body scene shots. The same phrasing feeds both the composer prompt and the final render prompt. The composer also gets the scene setting + time-of-day (from scene memory) for lighting and the **last 2 exchanges' narration** (budgeted excerpts, newest largest). It designates ONE focal character from the pool — or none: an empty room composes a **location-only POV shot**, a legitimate output, not an error — plus which other roster members are in frame. The output is clamped server-side (`resolveScenePlan`): a focal name not in the roster is replaced (`images.scene_composer.focal_clamped`), invented "others" are dropped (`images.scene_composer.absent_character_dropped`), and every character's outfit phrase is forced from wardrobe state — prose lies.
   - **Bare-region phrasing** (`exposedRegions` + `formatExposure`): listing only worn garments isn't enough — image models default every subject to fully clothed, so a removed top never shows. From each NPC's coverage we classify torso (`chest`), lower body (`pelvis`/groin·hips), legs (`thighs`), and feet — `covered` / `sheer` / `bare` — and inject explicit phrasing ("topless, bare chest", "bare below the waist", "bare legs", "barefoot", or a single "fully nude" when torso+pelvis+legs are all bare). Chat wardrobe state is authoritative: if a character has no worn clothing items, `exposedRegions([])` is the current outfit state and the render prompt says they are nude rather than keeping a clothed reference avatar. **head/hands are deliberately omitted** (bare there is the universal default and would fire on everyone); **feet are included by choice** — and since pants stop at `ankles`, an NPC with no modelled footwear reads barefoot.
2. **Render**: image generation is **Venice/Qwen end-to-end** (Flux/OpenRouter removed from the image stack 2026-06-19). References anchor on the character's **library avatar** (`findParticipantAvatar`). **Two reference modes** (`SceneGenState.referenceMode`): **single** (default) anchors on ONE avatar (the focal's when ready, else the first roster member with a ready avatar — `images.scene_render.reference_fallback`, info — the focal then described textually); **multi** gathers every roster member's avatar in plan order and feeds up to 3 (`findSceneAnchors`; characters prioritised, dropped past the cap) to Venice `/image/multi-edit`, identity-locking each. Either way the other/overflow characters are described textually (appearance summary + state-forced outfit + action). The prompt asserts coverage state both ways — listed garments **and** bare regions — and closes with "depict only the clothing described … add no garment that is not listed", so the edit model can't re-paint a shed garment back onto the (fully-dressed) reference avatar. **Venice caps the edit prompt at 1500 chars** (`VENICE_RENDER_PROMPT_LIMIT`); untruncated garment descriptions blow that easily, so on **both** Venice edit paths (single + multi) `buildSceneRenderPrompt` progressively excerpts the outfit + setting text until it fits (word-boundary hard clamp as a final net) — identity lock, POV rule, pose, and bare-region phrasing are never dropped. Text-to-image (`venice_generate`) is unbudgeted and renders on the shared default pick (`veniceSceneImageModelId` → Chroma since 2026-07-10; the edit rungs necessarily stay on the Qwen edit models — Chroma has no edit variant). **Provider routing & fallback ladder** (scene-images.spec.md §4/§8.3): the inline if-branches are gone — `renderSceneImage` builds a `SceneVisualReference[]` (the featured characters + location, with each available avatar's image + the location image + provenance attached) plus a `referenceBuffers` map (`imageId` → bytes), and `routeSceneProviders` picks an ordered chain from the capability registry `IMAGE_PROVIDERS` (`server/ai/image-providers.ts`, a typed code registry, not a DB table): multi-reference edit (`venice_multi_edit`, mode `multi`, when ≥2 reference images exist) → single-reference edit (`venice_edit`, when ≥1 anchor image) → text-to-image (`venice_generate`, the shared Chroma default) → demo monogram. The caller's **`mode`** (`single`|`multi`, threaded `renderResolvedScene` → `routeSceneProviders`) only prepends the multi rung; it never blocks a render — `multi` degrades to the single ladder when fewer than two reference images are available. Character-chat scenes are single-reference by default (one subject, no location image) — and the scene strip's **per-chat model pick** (`character_chat_state.scene_model`, contracts `chatSceneModels`, owner request 2026-07-11) can hot-swap the route: `"reference"` (default) keeps the identity-locked Qwen single-edit; a t2i key (chroma/qwen/lustify/illustrious/turbo) deliberately drops the avatar anchor and renders text-to-image with that model (`t2iModel` threads `renderResolvedScene` → `renderVeniceGenerate`, and `images.meta.model` labels it) — a style swap where identity rides the prompt's appearance/anchor lines instead of the reference. The executor walks the chain with a **reason-keyed retry** — a **transient** failure (timeout/5xx/429, classified via `classifyImageFailure` reusing `describeImageGenError`) retries once on the same provider; a **content rejection** (moderation) never retries and drops to the next rung. Each provider gets its **own** prompt (single-edit, multi-edit, and text-to-image are distinct builders), so a text-to-image fallback never carries the identity-lock block (`allowIntimate` rides the image refs' `allowForIntimate` — for multi, every featured character ref must clear it; permissive today; the deferred uploaded-avatar guard, spec §3, flips it). Every downgrade logs `images.scene_render.provider_fallback` (info, `{from,to,reason}` — including the upstream Venice error message); a chain where every rung failed transiently logs `images.scene_render.service_outage` (warn). These diagnostics were long **black-holed** — no caller threaded a `DiagnosticSink`, so an identity-locked edit silently degrading to text-to-image (the character no longer resembling its reference avatar) left no trace; `renderResolvedScene` now tees them into a `DiagnosticCollector` and **drains it to the server log** (`drainSceneDiagnostics`, `images.scene_render` scope) on every render, staying quiet on the success path (which pushes nothing). This is strictly more resilient than before — a Venice failure used to mark the row failed; it now degrades down the ladder.
   - **Subject body reveal** (`imageReveal` tag, docs/contracts/attributes.md): the identity reference is a **waist-up** portrait, so it locks the face and upper body but underspecifies the figure below it. `buildSceneRenderPrompt` therefore supplements the identity-locked subject with a body line built from attributes tagged `imageReveal`: `"shape"` (silhouette that reads *through* clothing — breast size/shape, waist, hips, leg build/length, foot size) is described **always**; `"skin"` (surface detail — nipples, leg hair, toenails, foot arch) only when its region reads **bare/sheer**. Split by sensitivity via `sceneRevealAppearance(…, {intimate})`: the SFW lower-body half (`Body (below the portrait's framing): …`) rides every route; the intimate half (breast silhouette always, nipples/anatomy when exposed) rides only the uncensored route, exactly like the existing intimate phrase. Untagged intimate anatomy (vulva/penis) keeps the plain exposure gate, so nothing is lost. **Today this is wired on the character-chat scene path only** (`images/character-scene.ts`, the iteration ground for image-prompt tuning — its outfit + exposure come from the chat state's free-text `outfit` and `outfit_exposed`, never `profile.defaultOutfit`: seeded from the scenario modal's Starting Outfit — which itself now falls back to the character form's `defaultOutfit` when blank — and **kept current by the archivist's `outfit` field** as the fiction dresses/undresses the character (chat-scene-fidelity slice 1); see [developer-notes/character-chat-scenario.plan.md](developer-notes/finished/character-chat-scenario.plan.md)); avatars keep strict exposure gating until the tag is adopted there. Tuning which fields reach the model — or flipping one between shape/skin — is a one-line registry edit on the attribute. **State-aware chat scene (character-chat-state-narration.spec.md §8):** `buildCharacterSceneContext` also folds the chat's live state into the shot — active conditions overlay attributes via `conditionAttributeOverlays` (so a "disheveled"/"unwashed" condition renders that way, with the same inherent-attribute guard as the prompt), and `visualStateNote(meters)` appends a render-tuned visible-state phrase (glassy-eyed and unsteady from intoxication, lank/sheened from low hygiene, heavy-lidded from low energy, breath shallow from arousal) to the subject's appearance. The route threads `chatState.meters`/`conditions` in; mood/affect ride the avatar reference, not this note. **No skin-colour words anywhere in an image prompt** (scene-pov-embodiment.plan.md slice 0, owner report): "flushed"/"blushing"/"rosy" render as **stage blusher** — a clown-makeup face, not a body state — so every meter phrase states physiology the model paints as physiology instead (eyes, lips, breath, sweat, posture, hair). Two leak paths, both closed: `visualStateNote` is the deterministic one (it used to say "flushed" in three of five phrases), and the **composer echo** is the LLM one — the narrator's own arousal threshold hint says "flushed skin" (`contracts/meters/registry.ts`), so the composer reads it in the recent narration and hands it back in `pose`/`mood`. `SCENE_COMPOSER_SYSTEM` rules against colour words *and* `scrubBlush` (`images/prompts.ts`, applied to `action` in `characterSpec` and to `mood` in `resolveScenePlan`) drops any surviving clause whole — the rule alone is not trustworthy, same belt-and-braces as `scrubPlayerFromAction`. Deliberately **not** scrubbed: `skin.undertone: rosy` is an *authored identity attribute* (the registry is the author's intent, not the composer's slip), and the narrator's hint itself stays — narration isn't rendered. **Setting from scene memory (chat-scene-fidelity slice 2):** `queueChatScene` derives the `room` from the chat's scene memory — the current place's background **sketch** when the `chat_scene_sketch` agent has written one, else its established name + details — and threads `sceneMemory.timeOfDay` through (was hardcoded `"day"`); an empty memory keeps the `DEFAULT_CHAT_ROOM` placeholder. **Identity anchors (slice 3):** `identityAnchorSummary` (whitelisted identity-critical attributes — skin tone/undertone, lips, eyes, hair, face shape/freckles) rides `ScenePresentCharacter.identityAnchors` on the chat context builder, and `buildSceneRenderPrompt` emits it **only for the identity-locked reference subject**, worded reference-authoritative ("Same person as the reference image — … the reference is authoritative where they differ") so it reinforces the lock without overriding the avatar; the multi-reference path gets the same per-anchored-character phrase. **Player-free poses (owner report 2026-07-10):** the composer's pose/activity rules require each phrase to be paintable with the character ALONE — player-directed beats translate to their solo equivalent (gaze/orientation → "toward the viewer"; contact/leading dropped, expression and energy kept — worked example in `SCENE_COMPOSER_SYSTEM`), and pose vs activity must carry distinct beats (no smile in one and laugh in the other). A deterministic backstop, `scrubPlayerFromAction` (applied in `characterSpec`, so composer text and the posture/activity fallback both pass through it), rewrites gaze-type player references to the viewer and drops any clause still naming the player; pronoun references are deliberately left to the composer rule (in a multi-character scene a pronoun may be another character). `resolveScenePlan` also strips trailing periods before the pose+activity join (no more `…smile.; Leading…` stitches). **Chat-keyed + message-anchored (slice 9):** every chat scene row carries `images.chat_id` (FK, **SET NULL on chat delete** — the asset survives in the Gallery) and `anchor_message_id` (plain text, no FK — the assistant line the scene illustrates, captured at **queue time**: the newest assistant line for a manual render, the exchange's own reply for an auto render; a dangling anchor — deleted/snipped message — degrades to strip-only, never an error). `GET /api/chats/:id/scene` lists **only** the conversation's own rows — sibling chats with the same character never leak in, and un-chat-keyed rows surface solely in the Gallery; ready anchored scenes render **inline in the transcript** under their message ([ui.md](ui.md) §The conversation page). **Auto at big moments:** with the chat's `sceneAuto` set to `"milestones"` (scenario-modal toggle), a stage crossing or strong reaction queues a render anchored to that reply via the shared `queueChatScene` — deduped to one live render per chat, fire-and-forget (a failed queue log-warns, the settled reply is never touched). A scene keeps its queue-time anchor, so a reply later replaced by "another take" leaves the moment illustrating the superseded beat — acceptable. Deleting a conversation scrubs **prompts per chat** for chat-keyed rows (sibling conversations keep theirs); legacy null-`chatId` rows keep the character-wide scrub.

The scene row is **chat-keyed** (`images.chat_id`). `GET /api/chats/:id/scene` lists the conversation's ready scenes (each entry carries its generation `prompt` for the **dev-only lightbox prompt panel**, docs/ui.md) — DB-backed, so an in-flight render survives page refreshes and resurfaces there when it completes; the conversation page polls while a `chat_scene_image` job is live or a pending row exists ([ui.md](ui.md) §The conversation page).

**Scene references (`image_references` join table):** at render, the scene records what it features — the focal + other in-frame characters resolved to their library `characterId`, the active location, and the identity anchor's avatar (with provenance) — as **one row per reference** in the `image_references` table (`recordImageReferences`), the **authoritative, queryable** record (docs/database.md). Columns: `kind` (`character`/`location`, with `style`/`pose`/`layout` reserved for multi-reference providers), `entity_id` (library id; null for non-entity roles), `role`, `source` (`generated`/`uploaded`/`composite`/`entity`; null = unknown), `image_id` (the asset actually fed to a provider; null when textual-only), `name`. FK-cascade on the scene image, so every delete path drops the rows automatically. This **replaced** `images.meta.references` (a one-time idempotent `scripts/backfill-image-references.ts` copied existing scenes over so they keep their facets); the contract split is `SceneVisualReference` (the render-input superset) vs `SceneReference` (the Gallery DTO the table projects to). It is still **forward-only** (older scenes that pre-date the backfill carry none) and is the seam a future multi-reference image model consumes, even though today's render still anchors on the single avatar above. The **Gallery hub** (`/gallery` · `GET /api/gallery` · [ui.md](ui.md); library-ux.plan.md §Follow-up pass) is tabbed by `images.kind`: **`?tab=scenes`** (default) lists every owner's **ready** character-chat scene in one keyset-ordered query (`entityKind:"character"` — owner-scoped character join, so a deleted character drops them; chat-keyed via `chat_id` since slice 9, which deleting the conversation SET-NULLs — the asset stays here, prompt scrubbed); **`?tab=portraits`** lists `portrait_variant` rows joined to their character; **`?tab=entity`** lists `entity` art with the source location/item name resolved. Every tab pages by the **keyset cursor** `?cursor=<createdAtMs>_<id>` + `?limit` (default 100, cap 500 — the old single-payload cap; a garbage cursor degrades to page 1) with a "Load more" button client-side, and carries the **`favorite`** flag (`images.favorite`, migration 0036; `PATCH /api/gallery/:id {favorite}` toggles it, optimistic heart on the tiles, a Favorites filter chip narrows every tab). Scenes group client-side by **view mode** — character / timeline — and filter by **avatar chip** character filters (the `character` refs sourced server-side from `image_references`, not `meta`). Deletion — the hover ✕, the **Select**-mode multi-delete, and the filter-scoped **Delete all** — runs `DELETE /api/gallery/:id` / `POST /api/gallery/delete {ids}` → `deleteOwnedImage(s)` guarded to the gallery's kinds (`GALLERY_IMAGE_KINDS`: scene · portrait_variant · entity — never avatars, chat uploads, or look/place anchors), then `clearEntityImagePointers` nulls any soft pointer at the deleted ids (a character's `avatar_image_id`, a location/item `image_id`) so nothing dangles — the portrait studio's own avatar-less-never-dangling rule. It's a clean 100% delete: every gallery view *and* the conversation page's scene strip derive live from the `images` table — there's no cached image id — so the image leaves every view at once.

Failures mark the job + image row `failed` with the error; the conversation is never blocked by image work.

### Chat selfies (character-sent photo messages)
`meta.flavor: "selfie"` on kind `scene` ([developer-notes/chat-selfies.plan.md](developer-notes/finished/chat-selfies.plan.md), docs/character-chat/images.md §Selfies): the chat scene pipeline with `SELFIE_FRAMING` swapped in for `SCENE_POV_RULE` (the exact inverse — the subject's own phone camera, arm's-length or mirror, aware of the lens) via the `framing` option on `buildSceneRenderPrompt`/`renderResolvedScene`. **Always the identity-locked reference route** (owner ruling — the per-chat `scene_model` t2i pick is ignored), and a **retry-once failure policy** replaces the ladder's silent degrade: classify the first failure (`classifyImageFailure`), retry once (content rejection ⇒ a sanitized plan — exposure/intimate phrasing stripped; transient ⇒ as-is), drop the failed first row, and let a second failure stand as a debuggable `failed` row (the transcript shows a "Failed" placeholder; its prompt is the admin lightbox panel). Diagnostic: `images.selfie.retry` (info).

### Chat reference anchors (current look + place)
`kind: "chat_look"` / `kind: "chat_place"` ([developer-notes/chat-scene-references.plan.md](developer-notes/finished/chat-scene-references.plan.md), docs/character-chat/images.md §Scene reference anchors): a conversation's cached render anchors. The **look** is an identity-locked Venice edit of the avatar wearing the archivist-tracked outfit (`chatLookKey` = outfit + exposed + appearance overlays; keep-latest-only; minted by the detached `chat_look_image` job on outfit/appearance changes in image-active chats — owner rulings). Scenes and selfies anchor on a fresh look instead of the always-dressed avatar, so render prompts stop fighting the reference's clothes. The **place** is a t2i establishing shot of the current scene-memory place minted lazily from its sketch (`chat_place_image`, CAS onto `ScenePlace.imageId`); once present, chat scenes render **multi-reference** (look/avatar + place) through the same `venice_multi_edit` rung sessions use. Both are chat-keyed, Gallery-hidden, hard-deleted with the conversation (`deleteChatAssets`).

### Chat photo attachments (player upload → vision input)
`kind: "chat_upload"` ([developer-notes/chat-image-input.plan.md](developer-notes/finished/chat-image-input.plan.md), docs/character-chat/images.md §Player photos): up to 4 player photos per chat message, uploaded via `POST /api/chats/:chatId/attachments` (`uploadChatAttachment` — same decode bomb guards as the avatar upload, fit inside 1280px, row-before-file, chat-keyed). **Input-only**: never an identity anchor or edit reference (the parked uploaded-avatar intimate guard remains the launch blocker for that), never in the Gallery, and — unlike scenes — **hard-deleted** with their message / conversation (`deleteChatUploads`; `deleteChat` removes them before the FK would SET-NULL them into limbo). At exchange time ONE batched vision call (`engine/chat-vision.ts`, `visionModelId()`) describes every photo on the message; the reads persist on the message meta (regenerate never re-spends) and reach the narrator as a fenced seen-channel tail block under chat rule 17.

### Entity images (items & locations)
Library items and locations each carry one image (their `imageId` column), generated from the entity's own fields — no character-style variants, no upload, no gallery. `generateEntityImage({ entityKind, entityId, userId })` (`server/images/entity.ts`) builds the prompt, creates a `kind: "entity"` asset, generates (demo monogram fallback), and on success sets the row's `imageId` and **reclaims every other image for that entity** (a regenerate replaces the old one — single image per entity, no orphans). Prompt builders (`prompts.ts`): `buildItemImagePrompt` is a catalog product shot (clothing on a ghost mannequin, objects isolated on a seamless surface; aspect 1:1); `buildLocationImagePrompt` is an establishing shot whose type follows the location's **scale** — `open`/`expanse` → outdoor landscape, otherwise an architectural interior (aspect 3:2), always empty (no people). Triggered by `POST /api/{items,locations}/:id/image` as a background `entity_image` job (survives navigation); the editor's **Image** tab polls `GET /api/{items,locations}/:id/image` (latest row) until it leaves `pending`, shows the result with click-to-enlarge, and offers Regenerate. Entity deletion already drops these via `deleteEntityImages`. The library pages also carry a **Generate images** button: `POST /api/{items,locations}/images` takes the ids the client sends (those visible under the active type/search filter — so the Items library's All/Clothing/Object/Container buckets scope the batch), intersects them with the owner's still-missing entities (`missingEntityImageIds`), and runs `generateEntityImagesBatch` — parallel batches of `ENTITY_IMAGE_BATCH_SIZE` (5), one failure never aborting the rest — in a background job; the grid polls so images appear as they land. The button opens a confirm dialog naming how many images will be generated; entities that already have an image are skipped.

## Image understanding (vision input)

The reverse direction — a model **looking at** a stored image — exists since the
character-sheet forge's portrait→attributes pass
([authoring.md](authoring.md) §In-sheet forge). It runs on **OpenRouter, not
Venice** (Venice is generation/editing only here): `generateChecked` accepts an
`images` option (raw bytes or base64 + mediaType, sent as message image parts) and
`visionModelId()` (`server/ai/provider.ts` `MODEL_DEFAULTS.vision`, currently
`qwen/qwen3-vl-235b-a22b-instruct`) is the code-default vision model — no override
layer. First consumer: `server/authoring/portrait-attributes.ts`, which reads a
character's ready avatar (bytes via `absoluteImagePath` + `fs.readFile`) and emits
closed-vocabulary attribute readings. Demo mode degrades to schema defaults (an empty
reading), never an invented one. Second consumer: the **chat photo read**
(`server/engine/chat-vision.ts` — one batched call describing a message's attached
photos, degrading to "a photo you can't quite make out"; §Chat photo attachments).
Add a vision consumer the same way: closed output
vocabulary, `generateChecked` + `images`, ground the output, degrade to a no-op.

## Demo mode

No keys → SVG monogram placeholder (deterministic gradient from the entity name) saved through the same registry path, flagged `meta.demo: true`. Every pipeline is exercisable in CI.

## Adding a pipeline

New generation kind = new `images.kind` value + a job type + a builder in `server/images/`. Use `generateChecked` for any prompt-composition step and the atomic-write helper for files. Update this doc.
